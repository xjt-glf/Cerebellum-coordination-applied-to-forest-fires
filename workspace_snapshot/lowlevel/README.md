# 低层任务条件强化学习策略（输出 9 个离散动作）

> 输入：环境状态 + 任务标签 τ + 任务建议 advice　→　输出：**每架无人机 9 个离散动作之一**
>
> 任务标签是**输入**，不是输出。高层（现在是课程采样，将来是 LLM Task Planner + ReAd critic）
> 只负责给 τ 和 advice；动作 0–8 全部由本模型直接产生。

## 1. 结论：可行

- 动作空间本来就是 `spaces.Discrete(9)`，`step(actions: List[int])` 全机同步，接口无需改动。
- 原项目的低层是**手写启发式**（`Training/DQN高层代码.py:672 option_to_action` → `heuristic_action_using_map` /
  `step_comm_support` / `step_go_charge`），高层是 3 个 option 的 Dueling DQN（K=10）。
  也就是说"可学习的低层"是空白，不会破坏已有成果。
- 环境实测速度：单进程 ~257 步/s，4 进程 ~678 env-steps/s。200 万步约 1–2 小时（8–16 进程更快）。
- 奖励可学性已通过自检：`python3 lowlevel/sanity_check.py` → **PASS**（贪心策略在三个任务上都显著优于随机）。

## 2. 对原环境的改动（已备份 `Env/低层环境.py.bak_*`）

| 位置 | 改动 | 原因 |
|---|---|---|
| `UAV.__init__` | 新增 `e_max / blocked / oob / recharged / depleted` 等逐步事件标记 | 奖励需要区分"撞墙""被队友堵住""刚补给""电量耗尽" |
| 新增 `GridEnv.energy_cost` / `energy_cost_mode` | **每步能耗统一为常数 2.5**（原为 `uav.e -= idx+1`，第 i 架耗 i+1） | 机队是同构的（都是 `e=300, d=5`），能耗不该随索引变化。索引相关的能耗会让各机在不同时刻耗尽，从**物理层面伪造出"分批返航充电"**的现象，而它其实与策略无关。取 2.5 = mean(1,2,3,4)，保持 4 机编队机队总能耗与历史实验一致，旧结果仍可比较。设 `env.energy_cost_mode = "legacy_index"` 可复现历史数值，但不应用于新实验 |
| 新增 `GridEnv._consume_energy()` | 能耗夹紧到 `[0, e_max]` | 原实现无下界，200 步后电量跑到 **−500**，任何依赖电量的策略/奖励都失效 |
| `step()` 移动分支 | 越界/被阻挡时打标记并照常计电 | 原实现越界动作完全免费，策略会学会撞墙刷步数 |
| `step()` 补给判定 | 从 `if action < 8` 分支内**移到分支外** | 原实现下无人机停在补给点（action=8）时**不会充电**，最终耗尽。这是一个实打实的 bug |

`lowlevel/honesty_audit.py` 把这件事量化了（4 机全部执行 tau=1，观察耗尽时刻的离散度）：

```
energy_mode    policy    depl  depl_std  depl_spread  blackout  mean_cov
legacy_index   random     2.2      17.5         40.0      93.0     0.225
legacy_index   greedy     3.0      31.2         75.0       6.4     0.905
uniform        random     4.0       0.0          0.0      21.0     0.440
uniform        greedy     4.0       0.0          0.0       5.0     0.885
```

`legacy_index` 下即使是**随机策略**，耗尽时刻的跨度也有 40 步——这说明错峰完全来自能耗差异，
不是学出来的。`uniform` 下随机与贪心的跨度都是 **0.0**（同时耗尽），这才是诚实的起点：
只有训练后的策略把 `depl_spread` 拉开、把 `blackout` 压低，才能宣称错峰是学到的。

这些改动都是向后兼容的（旧的高层 DQN 代码仍可运行），且修的是真 bug。

## 4. 状态空间 S（旧版 105 维，已被第 13 节的 352 维取代）

| 段 | 维度 | 内容 |
|---|---|---|
| `self` | 6 | x/50, y/50, e/e_max, d/5, **返航余量** (e − cost×d_station)/e_max, t/T |
| `agent_id` | 8 | 机身编号 one-hot ← 见下方说明 |
| `task` | 3 | 任务标签 τ 的 one-hot ← **任务条件的核心** |
| `advice` | 5 | priority_front one-hot(3), relay_spacing/20, proactive_handover |
| `map` | 49 | 7×7 **自身认知**火图 `uav.map_info/3`（与环境 r=3 的观测半径一致，未知=−1/3） |
| `fire` | 9 | 到探索前沿的 (单位向量, 距离)；到优先火线段质心的 (单位向量, 距离)；head/flank/tail 长度 |
| `comm` | 7 | 到最近**未覆盖**救援人员的 (单位向量, 距离)；到救援人员质心的 (单位向量, 距离)；覆盖率 |
| `energy` | 4 | 到最近**可用**补给点的 (单位向量, 距离)；max AoI/20 |
| `team` | 6 | 到最近队友的 (单位向量, 距离)；该队友的任务 one-hot |
| `coord` | 4 | 队内补给任务占比；队友最低电量/e_max；**我的电量在队内的排名**；我是否是最缺电的中继机 |
| `global` | 4 | 探索率、火点增量、风向单位向量 |

四个关键设计：

1. **不泄露全局真值火图**。局部图取自 `uav.map_info`（自身+队内融合的认知），而非 `grid["burning_state"]`。
2. **"最近可用补给点"而非"最近补给点"**（`nearest_free_station`）。环境的碰撞规则是"目标格冲突时只有索引最小的能进入"，
   若所有机都盯同一个站点，索引大的会被永久堵在门口直到耗尽。去冲突后的目标才可学。
3. **`agent_id` one-hot**。能耗统一后，同构机队 + 参数共享策略在数学上完全对称，会同时耗尽、
   同时返航、导致通信全断。给身份信息是让分工/错峰**可学**的标准做法
   （agent indication，Gupta, Egorov & Kochenderfer 2017），且不动物理设定——
   这与靠改能耗制造差异有本质区别：前者是给策略可用的信息，后者是替策略做决定。
4. **`coord` 段**。位置/电量/角色本来就是 PRS-HRL 假设全局广播的协同信号。
   其中"我的电量排名"和"我是否最缺电的中继机"是错峰能否学出来的关键——
   策略必须能判断"该我先走还是我该留下顶住"。

## 5. 奖励 R（旧版，已被第 13 节取代）

系数集中在 `reward.py: RewardConfig`，便于消融。所有引导项都用
**potential-based reward shaping**：`F = γ·Φ(s′) − Φ(s)`，`Φ(s) = −d(s)/D_max`
（Ng, Harada & Russell, ICML 1999 证明这种形式不改变最优策略，因此可以放心加大权重）。

**通用项**：时间成本 −0.01/步；越界 −0.30；被队友阻挡 −0.15；返航余量为负 −0.05/步；
电量耗尽 −2.00（**仅首次**）+ 之后 −0.05/步（且被迫悬停）。

**τ=0 火情感知**：每个新观测到的火线边界格 +0.15（落在 priority_front 上 ×1.5）；新观测普通格 +0.01；
重访且状态变化的边界格 +0.05；朝探索前沿的 shaping ×1.0。
计数**只统计本机 7×7 观测足迹内**的新增，避免吃到队友地图融合的功劳。

**τ=1 通信中继**：**独占**覆盖人数 ×0.20 + 共享覆盖人数 ×0.05；max AoI 惩罚；
与另一台中继机距离 < spacing/2 时 −0.10（防扎堆）；朝最近未覆盖救援人员的 shaping；
**通信全断 −0.30/步**、**覆盖率相对上一步的下降量 ×(−0.50)**；
`proactive_handover` 开启时，朝"返航余量已为负的中继机"靠拢的交接 shaping ×0.30（PRS-HRL 的 switching-aware）。
用"独占覆盖"而不是"总覆盖/机数"是为了解耦信用分配——否则多机扎堆覆盖同一批人却都拿满分。
覆盖连续性那两项是"离开前先交接"能被学到的直接压力来源，能耗统一后它们变得必不可少。

**τ=2 返航补给**：朝**被分配到的**补给点的 shaping ×1.5；抵达 +2.00，条件是
**离站→在站的跳变** 且 **入站前电量低于 0.6·e_max**（`arrive_need_ratio`）。

后面那个条件是训练中补上的：只判跳变不足以堵住刷分。满电的机可以在站点格和邻格之间反复跳，
每两步白拿一次 +2.00（≈ +1.0/步）。策略确实学会了这招——`recharge×4` 的回报冲到 330
（贪心基线只有 2），而"把没抢到站点的两台送去空闲站点"能省下的 −2.00 耗尽罚被完全淹没，
`n_depleted` 因此长期卡在 2.0 不动。加上"入站前确实缺电"的条件后，同一份权重在
`recharge×4` 上的回报从 +330 掉到 −28，续训后 `n_depleted` 降到 0。

补给点目标由 `obs_builder.station_assignment()` 做**全局**贪心最小距离匹配。
早先的实现只把"索引更小的队友的最近站点"标记为已占用，导致各机看到的空闲集合互相矛盾，
且队友一移动分配就翻转，势函数的目标每步抖动——表现为 `recharge×4` 里有两台停在
已被占用的站点旁边来回游走直到耗尽。

## 6. 算法：MAPPO

参考 Yu et al., *The Surprising Effectiveness of PPO in Cooperative Multi-Agent Games*, NeurIPS 2022。

- **Actor**（参数共享，最终交付物）：`LayerNorm → 2×[Linear(256)+ReLU+LayerNorm] → Linear(9)`，
  正交初始化（输出层 gain=0.01），输出 9 维 Categorical。
- **Critic**（中心化、**置换不变**）：输入 `[own_obs(93), mean(others_obs)(93), global(6)] = 192`。
  这样 2/4/6 架无人机共用一套参数，换编队规模不必重训。
- GAE(λ=0.95)、γ=0.99、clip 0.2、ppo_epochs 5、entropy 0.01、grad clip 10、Huber(δ=10) 值损失、
  running ValueNorm（对稳定性影响很大）。

## 7. 在另一台机器上的运行步骤

```bash
cd hrl_dqn_improve
pip install -r lowlevel/requirements.txt

# 0) 训练前必跑：确认奖励可学（应输出 PASS）
python3 lowlevel/sanity_check.py

# 0b) 诚实性审计：确认能耗已统一，错峰不再由物理设定伪造
python3 lowlevel/honesty_audit.py

# 1) 冒烟测试：几分钟内跑通全流程
python3 lowlevel/train_lowlevel.py --dummy-vec --n-envs 2 --rollout 64 \
        --total-steps 20000 --eval-every 5 --run-name smoke

# 2) 正式训练（n-envs 设为 CPU 核数 −2）
python3 lowlevel/train_lowlevel.py --n-envs 16 --rollout 200 \
        --total-steps 2000000 --task-sampler mix --run-name lowlevel_v1

# 3) 验收
python3 lowlevel/evaluate.py --actor lowlevel/runs/lowlevel_v1/actor_best.pt
python3 lowlevel/honesty_audit.py --actor lowlevel/runs/lowlevel_v1/actor_best.pt
```

`--task-sampler` 四档：`single`（全队同任务，先验证单任务能力）→
`balanced`（保证至少一台感知一台中继）→ `mix`（每机独立均匀采样，泛化性最好）→
`mix+single`（30% single + 70% mix）。

**正式训练用 `mix+single`**：纯 `mix` 下"全队同任务"只占 1/3^3 ≈ 1.2%，
而验收考的恰好是 `sensing×4 / relay×4 / recharge×4`。尤其 `recharge×4` 里四机争抢
补给点的避让，在 `mix` 采样中几乎见不到，只用 `mix` 训出来的策略在该场景下会稳定残留耗尽机。

采样吞吐：`env.step` 约 13 ms 且是重尾分布（救援人员重分配会走 BFS）。
一进程一环境时主进程每步都在等最慢的那个 worker，128 环境的单步能被拖到 200+ ms。
用 `--envs-per-worker 4` 让一个 worker 顺序跑 4 个环境，重尾被平均掉、管道往返也降到 1/4，
实测吞吐从 ~250 sps 提到 ~800 sps。GPU 只跑 actor/critic，占单次 update 不到 5% 的时间，
想提速要么加大 `--envs-per-worker`，要么多卡并行跑多个超参变体，改网络规模没用。

**验收标准**（达到后再接大模型）：
- 三个任务标签下 policy 回报都显著高于 random；
- τ=1 的平均覆盖率 ≳ 0.85；τ=0 的平均探索率 ≳ 0.75；τ=2 的 `n_depleted` ≈ 0；
- `evaluate.py` 末尾的**任务建议敏感性**测试中，改变 `relay_spacing` / `priority_front`
  能看到指标变化——说明 advice 真的被用上了，而不是被网络忽略。

## 8. 与 ReAd 流程的衔接

顺序很重要，不能颠倒：

1. **（本次交付）** 训练任务条件低层策略 → 冻结 `actor_best.pt`。
2. 用冻结的低层 + 启发式/LLM 规划器采集数据集 `D = {(s_t, τ_t, r_t)}`。
3. MC 回归训练 ReAd critic `Q_θ`（冻结 BERT + MLP(256,1) 头）。
4. 接入 LLM Task Planner，用 `S_ReAd(τ) = Q_θ^{1:i} − Q_θ^{1:i−1}` 与阈值 α 做重规划门限。

**为什么必须先冻结低层**：ReAd 的 `Q_θ` 是在固定低层执行器下回归出来的。
如果低层还在变，critic 的回归目标就是移动靶，训不出可用的打分器。

接入时只改一处——`policy_api.LowLevelController.set_task()` 的调用方，
从课程采样器换成"LLM 生成 → ReAd critic 打分 → `S > α` 才下发"。
`task_spec.TaskAdvice.from_llm_json()` 已经按 A2C-LLM 的 `AugParse` 风格写好容错解析
（字段缺失/非法一律回落默认值，不抛异常，由上层记 violation flag）。

## 10. 能耗统一后，高层必须跟着改（重要）

**"谁在什么时候去充电"是高层决策**（tau=2 的分配），低层只负责把 tau 执行好。
所以能耗统一之后，真正需要学会错峰的是高层，而现在的高层**结构上做不到**：

`Training/DQN高层代码.py:659` 的 `high_obs` 只有 14 维：

```
g(7) = wind_speed, explore_rate, fire_diff, head_len, flank_len, tail_len, coverage_rate
[7]  = battery_level        ← 只有"自己"的电量
[8]  = coverage_rate（与 g[6] 重复）
[9]  = self_dist_to_rescuer_center
[10] = min_team_dist_to_rescuer_center
[11:14] = task_ratio（上一步的任务占比）
```

其中 g、coverage_rate、task_ratio 都是**全队共享的量**，只有 `battery_level` 和
`self_dist` 因机而异。能耗统一后所有机的 `battery_level` 恒等，于是各机的
`high_obs` 几乎完全相同 → 参数共享的 DQN 输出同一个 option → **同时返航**。
这不是训练不充分，是观测里缺信息导致的结构性缺陷。

要让错峰真正学出来，高层观测至少需要补上：

- 队友电量的 min / max，以及**自己的电量排名**（`self_energy_rank`）；
- 队内已有多少台在执行 tau=2；
- 当前中继机里最低的返航余量（谁快撑不住了）；
- agent id one-hot（打破参数共享下的对称性）。

这四项我已经在低层观测的 `coord` + `agent_id` 段里实现了
（`obs_builder.py`，共 12 维），高层可以直接复用同样的计算方式；
`TaskConditionedEnv.global_features()` 也已经提供了队内最低电量。
**这一步我没有替你改高层代码**——它涉及重训你已有的 DQN 结果，需要你先决定
是重训还是换成 LLM 规划器。两条路：

1. 如果高层最终要被 LLM Task Planner 替掉（PPT 里的方案），那就别再投入重训 DQN，
   直接把队友电量/排名写进 LLM 的 prompt，让 ReAd critic 用 `S_ReAd` 去否掉
   "四台同时返航"这种低优势的计划——这恰好是 ReAd 最擅长的场景。
2. 如果论文还需要一个纯 RL 的高层基线，那就按上面四项扩展 `reconstruct_high_obs`
   并重训。诚实的做法是同时报告 `legacy_index` 与 `uniform` 两组结果，
   并说明前者的错峰来自能耗设定。

## 11. 已知风险

- **能量预算**：统一能耗 2.5/步、容量 300 → 单次续航 120 步，而 episode 200 步，
  因此每机每回合至少要返航一次。这个数值可用 `env.energy_cost` 调整：
  想让"是否返航"成为更强的权衡，调大到 3.0；想先降低难度做通路验证，调小到 2.0。
  **不要**用索引相关的能耗来制造差异。
- **能耗统一让问题变难了**（这是对的）：随机/贪心基线下 4 机同时耗尽、通信全断。
  低层能做的是"给了 tau=2 就高效返航""给了 tau=1 且要求交接就去补位"；
  真正的错峰调度责任在高层，见第 10 节。
- **通信奖励仍有团队耦合**：已用"独占覆盖"解耦大部分，但覆盖率本身是全局量，
  仍可能出现次优的分工。若收敛不佳，可把 `w_shared` 降到 0。
- **救援人员逻辑带来非平稳性**：救援人员每 3 步移动一次、目标 5 步强制重分配
  （`低层环境.py:1495-1654`），对低层策略而言是环境噪声。可训，但收敛会慢一些。
- **碰撞规则会静默吞掉动作**：已通过 `blocked` 标记显式扣分，让策略学会避让。

### 13.1 环境纠正（`Env/低层环境.py`）

### 13.2 指令结构（`task_spec.py`）

上层一次性给出全队指令 `TeamPlan{orders: [UavOrder]}`，每架无人机一个共享参数的策略只看自己那条。
任务建议从"抽象偏好"改成**显式目标**：

- 感知-搜寻：`{"task":"explore", "target":[x,y]}` 去哪片未知区域
- 感知-巡逻：`{"task":"patrol", "target":[火点中心], "ring_radius":"auto"}` 绕哪个火点、环多大
- 通信中继：`{"task":"relay", "rescuer_id":3}` 去覆盖哪个人员
- 返航补给：`{"task":"charge"}` 站点由环境做全局去冲突匹配

`TeamPlan.from_llm_json()` 沿用 AugParse 风格容错（字段缺失/非法一律回落默认值，不抛异常）。
接 LLM 只需替换 `TaskConditionedEnv.set_plan()` 的调用方，低层不用改。

三个必需的设计：

1. **全图粗视图**让"还剩哪片没探索"直接可读。旧版只给"火线前沿"，还没找到火点时那是空集，
   势函数没有梯度，策略退化成沿地图边界打转——这就是"无人机绕着地图边界转"的根源。
2. **搜寻的兜底目标取远处未探索粗块中心**，不是最近前沿格。前沿总紧贴自己足迹边缘，
   距离只有几格，梯度极小，原地悬停也不亏（实测 explored 只有 0.07）。
3. **`目标是否为火点`这一位不可省**。少了它，patrol 指令在还没发现火点时观测上与 explore
   无法区分，而奖励侧一旦发现火点就切到环半径势函数，两边会打架。

### 13.4 奖励 R

引导项一律用 potential-based shaping（`F = γΦ(s′) − Φ(s)`，`Φ = −d/D_max`）。

**通用**：时间 −0.005/步；越界 −0.30；被挡 −0.15；返航余量为负 −0.05/步；
耗尽 −2.00（首次）+ −0.05/步；**全队共享过火面积增量 −0.05/格**。

**τ=0 搜寻**：足迹内每个新探索格 +0.02（全地图）、每个新发现的燃烧格 **+0.30**、
朝指令目标 shaping ×1.0。重叠足迹按覆盖机数均分——共享观测下不这样会重复领功。

**τ=0 巡逻**：**每纠正 1 个"认知已过时"的格子 +0.05**。这里必须用"过时被纠正"而不是
"真值发生变化"：半速扩散下全图每步只有约 0.4 格状态变化，按后者给分几乎没有信号，
巡逻拿不到正收益（实测贪心不如随机）。环半径 shaping ×1.5，**半径自动取 √(size/π)+2**
（写死 6 格会让无人机在更大的火场里面绕，白吃惩罚）；停在燃烧格 −0.05。

**τ=1 中继**：独占覆盖 ×0.20 + 共享 ×0.05；**信息投递 +0.02/格（单步上限 2.0）**；
通信全断 −0.30/步；覆盖率下降量 ×(−0.50)；扎堆 −0.10；朝指定人员 shaping；交接 shaping ×0.30。

**τ=2 补给**：站点全局去冲突匹配 + shaping ×1.5；抵达 +2.00，且要求入站前电量低于
`0.6·e_max`——只判"离站→在站"跳变不够，满电的机会在站点和邻格之间反复跳刷分。

## 14. 第二轮修正与最终交付

### 14.1 人员速度与寻路（按需求修正）

修之前实测：8 人 x 300 步里 **BFS 有 569 次返回 None**（24% 的步数），移动率只有 25%。三个原因：

| 问题 | 修法 |
|---|---|
| `is_blocked_for_people` 把 `burning_state > 0` 一刀切当障碍，**包括烧尽(2) 和已扑灭(3)** ——人员自己刚扑灭的格子立刻变成永久的墙，沿火线推进几格就把自己围死（当时 448 个"障碍格"里 168 个根本没在烧） | 只有 `0 < state < 2`（正在燃烧）才挡路 |
| 目标点设在**燃烧格**上，BFS 终点始终是"墙"；外圈被扑灭一圈后剩下的燃烧格被围在里面，直接不可达 | `known_fire_clusters` 新增 `approach` 集合 = 火线**外侧**的可通行格，人员目标落在这里（对应"不进火区、围着火区走"） |
| 灭火依赖"到达指定目标格才灭那一格"，目标被别人灭掉或被围住就白站着 | 新增 `extinguish_near_rescuers()`：每步扑灭每人切比雪夫半径内的燃烧格（`extinguish_radius=2`、`extinguish_rate=2`），对应"靠近就自动灭火" |

另外两个稳健性补丁：BFS 包围盒搜索失败后**全图重试**一次（包围盒会把绕开大火场的绕行路径切掉，误判为不可达）；BFS 真的失败时走一步贪心可通行邻格，不再原地干等。速度按需求改成每步 1 格（`rescuer_move_period=1`）。

效果：**BFS None 569 → 0**，扑灭格数 77 → 339。灭火强度标定过三档：`1/1` 只灭 19 格（太弱），`2/1` 灭 112–152 格，**`2/2` 灭 350 格、过火面积 0.0516 → 0.0357（−31%）**（第一轮只有 −2.5%）。

### 14.2 其余四处修正

- **补给点 4 → 8 个**（四角内缩 10% + 四边中点）：到最近站点的平均距离 ~28 → 15.9 格，最坏 55 → 40 格。原来常有 2/4 台在通勤。
- **`coverage_rate` 改成只算无人机覆盖**，与奖励口径统一；另存 `comm_coverage_rate`（含基站）供 blackout 判定——人员在基站圈里时无人机覆盖为 0 但通信是好的，不该罚中继机。改前随机策略也能拿 1.000（毫无区分度），改后随机 0.000–0.301 vs 贪心 0.461–0.876。
- **回合 300 → 600 步**，让"探索完毕 → 转巡逻"两个阶段真能跑完。
- **风向与火点数每回合随机**（风向 0–2π 连续、火点 2–4 个）。风向必须同时进观测（`global` 段 6 → 8 维，补 cos/sin），否则就是不可观测噪声。`OBS_DIM` 352 → **354**。

### 14.3 训练过程中发现并修掉的三个问题

**（1）fork 出来的并行环境在跑同一个回合序列。** 环境的随机性（可燃度图、火点位置、风向、无人机初始位置）全部走**全局** `np.random`，多进程采样是 fork 的、各 worker 全局随机状态完全相同，而 `TaskConditionedEnv` 的 seed 只喂给了指令采样器。实测 4 个 worker 的风向/火点数/火点坐标一模一样——**上一轮 6M 步的多样性只有名义上的 1/96**。修法：`_make_env` 里用本环境自己的 RNG 给全局流播种。

**（2）奖励权重在 600 步回合下全面失衡。** 上一轮跑到 6.6M 步时出现"**回报涨、任务指标跌**"：探索率 0.644→0.536、发现率 0.501→0.454、扑灭 310→255，只有覆盖率在涨。拿当时权重做单指令验证，`explore x4` 下策略只铺开 0.442（贪心基线 0.776）。把一个回合的奖励分项按任务累加（`lowlevel/_parts.py`）后原因很清楚：

```
comm_relay    total=-249.3  aoi=-276.1  cover=+87.5  team=-19.8  unsafe=-19.6  stranded=-18.0
fire_sensing  total=+135.6  sense=+258.2  team=-39.6  unsafe=-37.8  stranded=-36.0
```

四处修正：

- **AoI 惩罚无界、且用的是历史最大值**。`env.max_AoI` 是只增不减的 running max，`-0.02 x (max_AoI/10)` 一回合累到 **−276**，中继机怎么飞都摆脱不掉。新增 `cur_max_AoI`（当前值），惩罚改成有界的 `-0.10 x min(cur_max_AoI, 50)/50`。
- **覆盖奖励按人数给，量级压过一切**（每步最高 `0.20x8=1.6`，600 步 = 960；而探索全图铺开总共才 200）。改成按**人数比例**给（`w_exclusive 0.50`、`w_shared 0.15`），探索权重同时上调（`w_new_cell 0.02→0.04`、`w_new_fire_cell 0.30→0.40`）。
- **过火面积增量惩罚过重**（每机一回合 −20，与整个探索收益同量级），而该量噪声很大（配对测试差值均值 +0.0004）。`-0.05 → -0.02`。
- **`unsafe` / `stranded` 在 600 步下被放大**，探索机飞远执行任务反被重罚。`-0.05 → -0.02 / -0.03`。

修完的分项：`comm_relay +7.6`（aoi −50.1 已封顶）、`fire_sensing +196.4`。

**（3）最优权重的挑选标准。** 原来按 `eval_return` 挑，而回报被覆盖项主导，"覆盖很好但不去探索"的版本也能拿最高回报。改成综合分：
`0.35x探索率 + 0.25x发现率 + 0.20x人员已知火情 + 0.15x覆盖率 + 0.05xmin(1, 扑灭/400) − 0.10x耗尽比例`。

**（4）比率指标的口径。** 火情发现率/人员已知火情的分母是"当前真实燃烧格数"，人员灭火能力增强后回合末只剩个别燃烧格，末值剧烈抖动（出现过 `disc=0.000` 但 `explored=0.628`）。改成取**回合均值**，并新增 `n_extinguished` 作为单调可读的压制指标。

### 14.6 仍然存在的局限

1. **过火面积是噪声级指标**。6 种子配对测试（同一世界 random vs greedy）逐回合差值 [+0.021, −0.007, +0.004, −0.005, −0.001, −0.010]、均值 +0.0004，而 `ext` 分得很开（26–224 vs 381–474）。600 步里火有多个推进方向，8 人每步清 2 格追不上外沿。**验收请以 `n_extinguished` 为压制能力主指标**，过火面积只作参考。

### 15.2 合围（contained）语义

`known_fire_clusters` 新增 `contained`：某火区外圈八邻域里既无已知健康格(0)、也无未知格，全是烧尽(2)/已扑灭(3)/地图边界。

这在物理上成立——已扑灭格在 `update_burning_state` 里属于 `special` 掩码、永不改变，等价于隔火带，**合围后的火不会再扩散**。于是新增 `active_fire_clusters()`（未合围的火点）并接到三处：

1. 人员目标分配只看未合围火点，合围完就换下一处（不去灭被围起来的火）；
2. 规划器的巡逻目标、观测里的火点引导都只用未合围火点（不派无人机去侦查已合围的火）；
3. 观测 `fire` 段新增一位"已合围火点数/6"。`OBS_DIM` 354 → **355**。

**指标口径随之分成两套**（重要）：

- 训练时用的口径（`fire_discovery_rate` / `rescuer_known_fire_rate`，分母 = 全部真实燃烧格）继续进观测，避免训练/评估不一致；
- 评估用的口径（`active_discovery_rate` / `active_rescuer_known_rate`，分母 = **未合围**的真实燃烧格，合围判定按真值做）进 info 与验收表。

必须分开的原因：合围后按设计不再派无人机侦查，我们对那片火的认知必然变旧，用全部燃烧格做分母会让发现率在合围完成后跌到 0——那是设计的结果，不是策略变差（实测出现过 `ext=406` 但 `discovery=0.000`）。

顺带修了自检的一个判定 bug：`recharge x4` 的判定列索引写的是 6，但后来在 `rollout()` 返回元组里插入了 `n_extinguished`，导致它实际在比"扑灭格数越少越好"而误报失败。改成索引 7（`n_depleted`）。

### 15.6 人员运动规则收敛为"只在白格作业"（最终版）

按需求把规则钉死：**人员只能在白格（`burning_state == 0`，从未着火）上移动**——
燃烧中、烧尽(2)、已扑灭(3) 全部不可通行；感知到别处有火会分散作业。

这条规则单独加上去会立刻把人员困死，我按顺序定位并修了四个问题：

| 现象 | 定位 | 修法 |
|---|---|---|
| 76% 的人步"BFS 无路且贪心也无路" | 作业位（`approach`）只按"贴着火的白格"选，**没检查走不走得到**。绿色隔火带会把火线外侧的白格切成互不连通的口袋：目标本身合法，但通往它的唯一走廊已被已扑灭格封死（诊断里打出过 `RTGGX` 这种局部图——目标 T 与人员 X 之间隔着 GG） | 新增 `_white_components()`（白格 8 连通标号，按步缓存）与 `_reachable_ring()`，只在**与人员同一白连通域**的作业位里选目标。修完 BFS 失败率 76% → 0% |
| 10 个人全挤到 1 处火点 | 分配时把"可达性"当成了**第一排序键**、名额当第二键，于是"可达但名额已满"的火点压过"名额空着"的火点 | 改成先筛可达集合、再在其中优先取有名额的、最后按距离取最近 |
| 单人重选目标会让整队逐渐漂到同一处 | 白格连通域被隔火带切开后，单人只能挑"唯一还走得到"的那个 | 新增 `rebalance_every=25`：周期性用带名额的全局分配把人手重新摊开 |
| 人员被火追上后永久困在焦土里 | 焦土/已扑灭不可通行，四周没白格就出不来 | 脚下变成非白格时先撤：优先退到八邻域里"周围火最少"的白格；被完全包住时**允许踩烧尽/已扑灭格紧急撤离**（这是明确的例外，正常通行仍然只走白格） |
| 人员对某火点的记忆过时（记忆里的作业位现在全在火里），返回 None 后原地干等 | 认知与真值不一致 | 这种情况改为朝**火点中心**走，路上八邻域会不断刷新共享火图，走近后自然拿到真实外圈再转入绕圈作业 |

顺带去掉了一版"只往里打"的灭火约束——实测它对卡死问题无效（真正原因是可达性），保留只会让逻辑更绕。

### 15.8 "人员先跑到地图中间才分散"的原因与修法

**代码里没有"先去中心"的逻辑。** 历史版本 `move_rescuers_one_step` 里确实有一段
"没有目标就朝硬编码的 (40, 25) 走"（旧地图的火源位置），那段在第 13 节改人员感知时
已经删掉了；本次又 grep 复核过，除了 `base_pos=(0, W/2)` 和 `rescuer_start=(1, W/2)`
之外没有任何写死的中心坐标。

真实原因是三件事叠加，用轨迹追踪确认的：

1. **10 个人全部出生在同一点**（基站在地图左侧中点，起点 `(1, 50)`，原来只有 0.6 格的错开）；
2. **无人机是一处一处发现火点的**，前 100 步往往只有 1 处已知火 → 名额就是 10 → 全员被派往同一处；
3. 从 `(1, 50)` 走到那处火的直线恰好横穿地图中部。

追踪证据：t=40～120 十个人的目标全是 `(78, 51)`，位置从 `(10,50)` 一路同步推进到 `(50,50)`；
第二处火在 t≈120 被发现，锚点才分裂成两处，人员随即分流。所以"分散"的时刻 = 第二处火被发现的时刻。

**做了三处修改：**

- 起点从"一个点"改成**沿基站铺开一条横队**（10 人时 y 从 46 到 54，x 轻微错开），
  即使目标相同也是并行推进而不是一列纵队；
- 同一火点内的目标**沿外圈按角度均匀铺开**（`assign_rescuer_targets_by_cluster` 里
  先分名额、再按 `base + 2πk/m` 取角度最近的作业位），从多个侧面同时贴上去；
- `_cluster_headcount()` + `rebalance_every=25`，周期性把人手按名额重新摊到各活火点。

**试过并回退的方案**：给每个已知火点设人数上限（未探索完时每处最多 ⌈n/3⌉ 人、其余在基站待命）。
视觉上确实不再排队横穿地图，但压制能力掉得更多——扑灭格数 236→166、火情发现率也跟着掉，
因为待命的人什么都没干。已回退，代码里留了注释说明原因。

修改后的轨迹：t=20 十人沿 y=46～54 铺开待命；t=40～60 并行推进；t=80 分流到两处火点。

演示重录（seed 20000，3 火点 10 人，201 帧 / 6 fps）：
探索率 0.812、火情发现率 1.000、人员已知火情 1.000、扑灭 252 格、耗尽 0、过火面积 0.0485。

**仍需注意**：单回合方差很大。同样配置三个种子的扑灭格数是 252 / 162 / 229、
发现率 1.000 / 0.860 / 0.385。挑单个种子看会误判，评估要用多回合均值。
