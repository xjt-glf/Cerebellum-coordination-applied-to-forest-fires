## 1. 任务目标与优先级

你的任务是基于现有无人机—地面人员协同灭火系统，自主寻找可形成论文贡献的协同机制，并通过真实执行结果、对照实验和消融实验检验它。允许修改研究方案、淘汰无效方案，最终保留证据最充分的方向。

| 优先级 | 研究方向 | 核心问题 |
|---|---|---|
| 第一优先级 | Critic 给出精确、可操作的建议 | 如何从“计划评分低，重新规划”，走到“哪条指令有问题、依据是什么、具体改什么”？ |
| 第二优先级 | 推理延迟导致的决策过期 | 大脑思考时环境持续变化，返回的计划如何判断仍有效，并进行保留、局部修复或重新规划？ |
| 支撑工作 | 大模型与强启发式的比较 | 哪些场景值得使用大模型？反馈机制的收益是否超过强规则方法和额外推理预算？ |
| 暂不主攻 | 大模型微调、蒸馏和底层重训 | 可作为后续路线，但不要让这些工作占据本轮主线。 |

这里的“证明有效”指建立可复核的实验证据，不能预设结果一定为正。完整、可信的负结果和失败归因也是交付成果。不要通过挑选种子、改变评价口径或弱化基线制造优势。

你可以自主选择 Critic 结构、反馈表示、候选修复方式、训练方法与研究工具。下面列出的是候选问题和证据要求，不是必须逐一实现的算法清单。优先形成一个清晰主机制，再决定是否加入延迟机制。

## 3. 先处理这些会影响结论的事实

1. **网页当前是同步等待。** 在 webapp/server.py 中，调用 brain.plan 后才继续 env.step。API 等待时间不会自动推进火势、能耗和人员运动。这个设置可用于隔离反馈质量，但不能证明延迟鲁棒性。

2. **现有门限实验没有实际调用千问。** read_critic.py 的 eval_gating 使用随机采样计划与重采样，适合初步检验评分器，不能作为“LLM 理解了反馈并改进决策”的证据。真实反馈闭环需另建实验。

3. **历史配对检验包含被检验 Critic 的自举值。** _rollout_branch 返回 r + gamma × V(s_next) − V(s)，其中 V 来自当前 Critic。该量可诊断 TD 一致性，但不是独立的真实长期收益标签。正式建议验收还需有限窗口的实际任务指标，以及更长窗口或整局实测回报。

4. **前缀价值差不等于真实个体因果贡献。** 现有采集把同一完整计划的轨迹回报用于多个前缀特征。它可用于估计某种采样分布下的条件价值，但不能直接把相邻前缀 Q 差解释为“第 i 架无人机导致了多少损失”。需要检验顺序敏感性、采样分布与干预后的执行差异。

5. **可选 waypoint_assist 会直接覆盖部分 Actor 动作。** 主实验先关闭，或者为所有组使用同样的配置并单列辅助比例。高层方法不能凭额外动作接管获得不公平优势。

6. **“活火归零”不自动代表灭火成功。** 当前 stop_when_clear 的判据涉及真实活跃燃烧格；烧尽也可能使活火消失。统一终止口径，并结合合围、损失与灭火情况定义成功，不能把网页提前结束当成成功率。

7. **记录实际解析和执行的任务。** relay 中 rescuer_id 优先于 target；没有显式目标时还会自动选目标。保存 raw plan、parsed plan、resolved target 和 applied plan。字段修复或忽略不能伪装成原始决策正确。

8. **自然语言事件基线需要公平比较。** 当前 HeuristicBrain 忽略 event。若研究语言理解，可以单列这一能力差异；若研究任务分配或反馈机制，给各方法相同的结构化事件约束，增加能处理这些约束的强启发式，避免让基线因为“不读事件”必输。

9. **区分策略可知信息和评价真值。** 核对火情发现率、过火面积、人员已知比例及其他特征的来源。完整真值可用于离线监督标签和评价；运行时 LLM、部署 Critic 与修复器只使用声明的可观测信息。若某组获得更丰富地图或轨迹，增加同信息量对照组。

10. **不要假设每个 advice 字段已被底层有效利用。** 独立测量 target、mode、ring_radius、handover 等指令变化的执行影响。源码中的历史备注是检查线索，不是本轮实验结论。底层能力不足可能是诊断对象，也可能限制高层方法收益。

## 5. 第一方向：把 Critic 变成有依据的建议系统

主问题：在固定底层执行器下，如何识别计划中的执行瓶颈，并给 LLM 提供能改善真实任务结果的修改建议？

至少回答三个问题：

- **定位**：哪架无人机、哪条指令、哪个任务关系需要修改？
- **依据**：判断来自什么可观测事实或经过验证的预测？不确定性有多大？
- **建议**：修改任务、目标、接替顺序、执行期限，还是暂时保持？预计改善哪项任务结果？

区分下发前的预测性建议和执行后的进展反馈。它们可组合，但数据时间点和消融中必须区分，不能把未来结果送回较早决策。

### 5.1 候选机制，自由选择

| 候选 | 可以探索的方法 | 必须检验的问题 |
|---|---|---|
| 任务结果分解 | 分别预测探索增益、覆盖变化、能量风险、交接时间与信息时效 | 多头反馈是否比同信息量的标量反馈有效？ |
| 指令级干预 | 保持状态和其余指令，只替换一项任务、目标或参数，估计执行差异 | 是否真的找到有益修改？是否依赖昂贵在线仿真？ |
| 联合关系诊断 | 识别交接缺口、重复搜寻、多人覆盖遗漏、补给争抢等交互 | 单机评分是否遗漏了组合效应？ |
| 修复建议学习 | 学习候选修改的排序、推荐具体 edit 或失败类型 | 是否优于规则修复和同预算搜索？ |
| 可信度与拒答 | 校准预测或使用集成估计，在证据不足时减少修改 | 能否降低“把正确计划改坏”的比例？ |
| 反馈压缩 | 用结构化证据、局部编辑约束或短文字将诊断传给 LLM | 收益来自信息内容，还是更长提示词与更多推理？ |

先选 2–3 个有区分度的候选做小样本筛选，避免一开始实现所有模块。网络结构变复杂、提示词变长或者解释更流畅，都不能单独作为有效性证据。

规则和模拟器可以提供诊断标签或强基线。若最终方法主要是规则系统，准确报告其性质；若主张是学习型 Critic，需用消融证明学习部分超过规则。

### 5.2 反馈接口示意

以下只是格式示意，agent 可修改；没有实测含义。confidence 和 predicted_gain 必须由经过验证的机制产生，不能填入主观分数。

```json
{
  "plan_id": "example_plan",
  "snapshot_t": 100,
  "feedback_t": 100,
  "issues": [
    {
      "uav_ids": [1, 2],
      "type": "relay_return_conflict",
      "evidence_keys": ["return_margin", "handover_eta", "coverage_gap"],
      "suggested_edit": "安排 UAV1 接替 UAV2；结合实际返航余量决定交接和返航次序",
```

若局部修复涉及补给匹配、队友任务或公共覆盖变化，应重新验证受影响的联合计划。不要强制“只改一架”而忽略真实耦合。

## 6. 第一方向的数据与监督

推荐但不强制的流程：

1. 从启发式、真实 LLM、扰动计划和历史失败轨迹获取不同难度的状态与计划；避免只训练区分明显好计划和全随机计划。
2. 对同一状态生成少量有意义的局部修改。至少包含 task、target、rescuer_id 等语义接近而执行效果不同的修改。
3. 离线复制环境进行配对执行。显式保存环境内部状态，以及 Python、NumPy、Torch 和环境自身实际使用的随机状态；仅复制某一个全局随机状态可能不足。
4. 使用相同、预先定义的后续控制协议比较两分支。先用短窗口筛选，再用更长窗口或整局验证，避免将提前消耗电量误当成持久收益。
5. 生成结果差、诊断依据与编辑标签。动态交互可以导致共同原因和非加性效果，标签的因果含义限定于本仿真干预与控制协议。
6. 训练、校准和筛选 Critic，再接入 LLM 修改闭环，评价真实执行结果。

建议的局部修改价值是“修改计划与原计划在同一状态和后续协议下的实际任务收益差”。可以用回报、指标向量或排序标签学习；不要只把自身预测值的增加当成修改有效。

训练/验证/测试按完整回合或场景家族切分。同一地图的相邻片段、同一快照的 A/B 分支与派生修改，必须放在同一集合。故障标签、提示词、阈值和模型选择只使用训练或验证数据。锁定测试集后，不再根据其结果修改方案。

部署型建议不能读取测试状态的未来真值轨迹。在线完整模拟器分叉只能作为明确标记的 oracle 上界或独立高成本方法；所有时间和 rollout 成本都需计入。若通过离线分叉训练轻量预测器，分别报告离线数据成本与在线推理成本。

真实 LLM 可暂时不可访问；此时继续做数据质量、Critic 与模拟器实验，清楚标记其结论范围。最终宣称“反馈改善大模型决策”之前，必须完成真实模型闭环验证。

## 7. 主要对照实验

所有组使用同一 Actor、环境规则、事件序列、终止口径、信息权限和任务指标。统一模型版本、temperature、基本任务说明、初始候选计划来源和解析修复规则。

| 组别 | 定义 | 用途 |
|---|---|---|
| H | 强启发式任务分配；需要时加入结构化事件约束或任务匹配 | 判断复杂方法的实际价值 |
| L0 | LLM 周期规划，无额外 Critic 反馈 | 基础高层能力 |
| L1 | LLM 获得当前状态、历史任务与普通进展反馈 | 排除“只要多给状态就有效”的解释 |
| L2 | ReAd 风格标量优势/分数反馈，触发同模型重规划 | 主方向的直接近邻 |
| L3 | 根据确定性约束或简单规则给具体修复建议 | 排除学习型 Critic 只是复述规则 |
| L4 | 在相同候选/调用预算下，重采样、self-reflection 或候选排序 | 排除收益只来自更多尝试或直接搜索 |
| P | 候选精确反馈机制与 LLM 修复闭环 | 检验新增机制 |
| O，可选 | 完整仿真或事后信息支持的最佳候选选择 | 仅作上界，不能与部署方法混为同类 |

预算公平至少报告两种视角：相同 LLM 调用/候选预算下的任务效果；相近任务效果下的调用、token、时间和仿真成本。给建议额外生成多个候选时，对照组也应获得相同搜索机会。

LLM 修改实验尽量复用同一初始候选计划，进行有/无反馈的配对修正，以隔离初始生成随机性。缓存真实响应可以复现固定输入实验；状态已变化时不能把旧响应当成该新状态的真实推理结果。

第一方向可先用所有组共享的同步设置隔离反馈质量；这一阶段不作延迟鲁棒性结论。实测修复耗时和额外调用数随后必须进入第二方向。

## 8. 第一方向的关键消融

围绕已选机制做消融，不要求实现下面每一个候选。每次消融保持其他信息、预算、训练划分和执行条件尽量一致。

| 消融/对照 | 检验的解释 |
|---|---|
| 仅总分，对比诊断＋编辑建议 | 具体反馈是否比“请重新规划”更有效 |
| 给出问题定位但去掉编辑建议 | 增益来自诊断还是建议动作 |
| 所有新状态信息直接给 LLM，对比 Critic 整理后的反馈 | 排除信息量不一致 |
| 学习型建议，对比固定规则和同预算候选搜索 | 学习部分是否必要 |
| 去掉联合交互特征或交接关系 | 多无人机耦合是否贡献了收益 |
| 去掉不确定性/拒答 | 错误建议是否导致负收益 |
| 局部修复，对比全队重新生成 | 修改范围是否改善稳定性与成本 |
| 打乱/错配反馈、仅添加等长度通用提示 | 反馈内容是否被真正利用 |
| 直接应用同一建议编辑，对比让 LLM 根据建议修改 | 区分 Critic 直接求解与 LLM 吸收反馈的贡献 |

单列报告：建议正确但 LLM 未采纳、LLM 已采纳但 Actor 执行失败、建议本身错误、计划被解析器改写等失败类型。不能仅报告修改后 Critic 分数上升。

## 9. 第二方向：将等待期间的环境变化纳入实验

第二方向研究“计划在真正应用时是否仍有效”，不以 API 响应速度作为唯一目标。

先构建可复现的离散时间延迟实验，再评估真实 API 延迟。声明一个环境步对应多少秒；如果没有物理依据，用“延迟步数”和“延迟/规划周期”报告。该环境目前是栅格仿真，不能直接赋予它实机毫秒飞控含义。

推荐记录：

- 请求时快照、计划 ID、请求环境步与单调时钟时间。
- 返回环境步、实际应用环境步、旧计划与新计划。
- LLM、Critic、诊断、重新调用和局部修复的时间成本。
- 返航余量、覆盖、人员位置、已知火情、目标有效性等请求—应用变化。
- 保留、修复、拒绝、重新请求与降级原因。

主仿真线程拥有环境。后台规划只读取不可变快照，不能与环境线程并发修改同一对象。零延迟返回也需要合法初始任务，等待期间由各组共有的基础策略执行。

可以使用逻辑延迟队列，以预设步数安排计划返回，避免实际 sleep 冻结环境。真实调用则需单独定义环境的实时推进节奏，不能因为计算机仿真很快，就让等待几秒对应任意数量的环境步。

请求过期、响应乱序和事件更新时，定义计划版本规则，防止旧响应覆盖更新的有效计划。记录被拒绝或取消请求的成本。重新修复和再次推理也会延迟，不能给予新方法免费即时重算。

### 9.1 可探索机制

- 基于最新可观测状态检查目标、能量、覆盖和交接条件。
- 将计划质量评估从请求快照迁移到实际应用状态。
- 识别失效部分，保留仍可执行的任务并局部修复。
- 使用有依据的有效期、执行期限、完成条件或交接条件。
- 若预测返回时态势，学习预测器并校准误差；训练标签可来自历史未来，部署不能读取真实未来。

至少区分：

1. 实体或目标无效：目标已合围、人员位置变化、指定人员不存在。
2. 执行不可行：返航余量不足、接替未到位、资源冲突。
3. 价值过期：计划仍能执行，但当前已有更重要需求。

候选机制应超过“异步＋保持旧计划”和固定 TTL。规则时效检查是必要强基线；预测模型或复杂 Critic 必须证明额外价值。

### 9.2 延迟实验与消融

| 组别 | 定义 |
|---|---|
| D0 | 零延迟条件，仅用于衡量性能上界或任务基础，不用于宣称部署优势 |
| D1 | 环境持续运行，返回计划直接应用 |
| D2 | 异步保持旧计划＋固定 TTL/简单最新状态可行性检查 |
| D3 | 延迟机制：保留、局部修复或重新规划 |

初步测试可使用延迟 0、1/4、1/2、1、2 个规划周期，加上抖动、长尾延迟和突发事件；数值是建议起点，不是已验证配置。测试延迟范围与训练/调参范围分别记录。

在可比较条件下做 2×2 实验：精确 Critic 反馈开/关 × 延迟处理开/关。保持基础异步执行、状态权限、基础兜底与预算一致，观察两机制各自贡献及交互，不预设它们必然协同。

延迟消融可包括：固定 TTL、去掉最新状态验证、去掉局部修复、去掉返回状态预测、不同延迟估计误差。没有实现的组件不用强行加入。

## 10. 场景、指标与统计协议

至少覆盖普通任务、明确执行瓶颈和组合困难；用真实 LLM 产生的错误分布检验方法，不只使用专门为新方法设计的故障。

| 场景家族 | 需要检验的困难 |
|---|---|
| 常规探索—灭火 | 在没有明显故障时，反馈是否造成不必要的修改 |
| 中继—返航冲突 | 同时维持覆盖、按时交接和保存返航余量 |
| 目标重复或资源争抢 | 多机同目标、人员覆盖遗漏、补给点竞争 |
| 底层建议响应不足 | 合理高层指令在固定 Actor 下执行不佳 |
| 动态变化 | 人员移动、任务优先级变化、已知火情更新 |
| 泛化 | 未见地图/种子，以及能力范围内的机队规模、人员数与火点数变化 |

默认 Actor 身份编码和历史 Critic 槽位支持上限为 8。不要直接宣称任意机队规模或置换不变性；若研究扩展需单独实现和验证。

在正式测试前登记一个主要任务指标，以及能量与通信等守护指标。建议优先选固定任务期限内的过火损失或明确定义的成功率；高层综合回报可辅助报告，但不能替代原始指标。

| 维度 | 推荐记录 |
|---|---|
| 任务结果 | 过火面积、合围数量/比例、扑灭格数、成功率、合围时间 |
| 通信与信息 | 平均覆盖率、关键人员覆盖、最长连续中断、AoI 分布或超阈值步数 |
| 能量与执行 | 耗尽数量、返航违约、目标进展、任务完成时间、动作辅助比例 |
| 反馈质量 | 修改后实际收益、负收益建议率、定位/排序质量、校准、采纳率 |
| 协同成本 | 调用数、token、平均与尾部耗时、重规划次数、修改范围、角色切换 |
| 延迟影响 | 各延迟下的性能损失、有效性判断、拒绝后损失、事件恢复时间 |

“目标进展”必须按任务定义：巡逻不以不断接近火点中心衡量；中继不以距离缩短代替实际覆盖。比率指标可能因活跃火情分母变化产生波动，附原始计数和时间曲线。

统一失败与提前结束的处理。未完成任务的完成时间按删失或预先定义的失败惩罚处理，不能只对成功样本求平均而忽略失败。统一累计指标的时间范围，避免早停组因观测时间短而看似覆盖更好。

建议先做 5–10 个场景的小样本筛选，正式测试再固定至少约 30 个独立场景种子，按方差与成本扩展；这不是统计充分性的保证。学习型 Critic 尽量至少重复 3 个训练种子，真实 LLM 在固定场景下记录生成波动。资源不足时缩小结论范围并明确局限。

同场景配对比较，报告均值、离散程度、配对差与 95% 置信区间。以独立回合/场景作为重采样单位，不把相邻时间步当成独立样本。不同训练种子、API 重复与场景种子分层报告。

固定并保存外生事件序列；若动作改变了随机数消耗顺序，仅相同 seed 不足以保证相同外部扰动。多候选探索在验证集筛选，最终测试只用于事先选定的主要比较，报告全部正式实验。

## 11. 分阶段推进与停止条件

| 阶段 | 应完成的工作 | 决策依据 |
|---|---|---|
| A：核对与基线 | 核对信息权限、动作辅助、终止规则与底层响应；复现启发式和少量真实 LLM 结果 | 找到可重复的执行瓶颈，并确认基线没有被刻意削弱 |
| B：独立建议验收 | 不接 LLM，检验 Critic 是否能找到有益修改及识别不确定建议 | 实际 rollout 收益优于规则或随机修改，且失败类型可解释 |
| C：反馈闭环 | 对同初始计划比较普通反馈、标量反馈、规则建议与精确建议 | 真实 LLM 修改后的任务结果改善，收益不只来自额外调用 |
| D：主方向消融 | 固定方案、提示词、数据划分与预算，运行关键消融和留出场景 | 能解释增益来源，且未明显恶化守护指标 |
| E：延迟机制 | 环境在等待期间继续运行，完成 D1/D2/D3 与 2×2 比较 | 新机制优于基础异步/规则时效检查，并计入自身耗时 |
| F：论文判断 | 汇总强基线、负结果、置信区间、计算成本与文献差异 | 提炼证据支持的贡献，不以模块数量包装创新 |

若 B 不能可靠判断修改收益，先修复标签、信息与校准问题，不靠更复杂提示词掩盖。若 C 中 LLM 未利用建议，尝试反馈形式或任务适配；若直接执行编辑已经获得全部收益，准确定位贡献于修复器，而不是夸大 LLM 作用。

若 H 在常规场景始终更优，继续定位语言任务变化或复杂冲突中的适用范围；不要宣称大模型普遍更优。若 E 的规则时效检查已经解决问题，记录负结果，重新判断复杂延迟模型是否值得保留。

## 13. 最终交付与论文贡献判断

后续 agent 应交付以下可独立核查的材料：

- 研究报告：候选方法、文献差异、实验设计、正负结果、失败案例与建议下一步。
- 可运行代码：统一实验 runner、Critic/反馈实现、延迟机制（若进入第二阶段）、配置和明确复现命令。
- 原始证据：逐回合指标、逐决策日志、脱敏提示词与响应、数据划分、种子和外生事件序列。
- 版本清单：源码快照/版本、依赖、权重哈希、模型版本、方法 ID、关键实验开关。
- 统计与图表：主方法对照、关键消融、建议实际收益、成本；进入第二方向后再加延迟退化和 2×2 结果。

建议将报告放在 research_outputs/innovation_report.md，并为每个结论提供“主张—对照—指标—数据文件—统计结果—局限”的对应关系。所有路径与命令以最终实际产物为准，不留下占位引用。

完成研究不等于必须得到正结果。只有在以下证据成立时，才将某机制作为主要论文贡献：

1. 相对近邻方法的新增机制明确，并与已检索文献逐项对照。
2. Critic 建议改善独立执行结果，而不只是提高自身评分或生成更长解释。
3. 在公平信息与预算下，收益超过标量反馈、规则修复或候选搜索。
4. 留出场景与独立重复支持主要结论，守护指标、成本和适用范围清楚。
5. 第二方向若被采用，已证明处理了环境持续演化下的计划过期，并超过基础异步保持或简单检查。

最终论文可以围绕“执行依据驱动的高层计划诊断与修复”展开；只有第二方向也得到充分支持，再扩展为“推理延迟下的执行反馈与计划有效性协同”。标题和创新点以最终证据为准。
