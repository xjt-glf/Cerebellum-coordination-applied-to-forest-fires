# 分布式无人机任务分配器：MAPPO 训练实施与验收指南

版本：v2，2026-11-03。本文替换原固定四机、81 联合动作的 DQN 方案。  
实施对象：接手本任务的 Agent。本文只规定训练与验收；数值是待验证的工程起点，不是实验结论。

## 1. 目标与交付边界

训练一个**参数共享、分布式执行**的无人机本地任务分配器。每架无人机在各自的高层决策时刻独立选择：

- `0 / explore`：探索或复查区域；
- `1 / relay`：为地面人员提供通信；
- `2 / charge`：前往充电站补给。

同一套策略权重供所有无人机使用；输出层始终只有 3 个动作，不随无人机数量增长。训练阶段可以用团队信息训练集中式价值函数；执行阶段每机只运行共享 Actor，各自根据允许的观测与通信消息选择自己的任务。每机的高层任务再转成具体目标，交给现有冻结底层 Actor 执行移动。

首版用 **MAPPO，集中训练、分布执行（CTDE）**。训练混合 3、4、5、6 架无人机，测试覆盖这些规模并单列 7、8 架的未见规模外推。首先核实环境是否支持这些数量及人员数配置，不能将代码接受参数等同于有效支持；若存在地图、充电或底层 Actor 的扩展问题，先修实验适配并记录，不能隐瞒。

本阶段不调用 LLM，不训练“何时请示”门控，也不证明异步推理方案。人员沿用环境自动逻辑。未来该分配器可作为大脑等待期的本地处置模块。本次交付：源码、配置、Actor 和 Critic 权重、可恢复 checkpoint、通信/目标协议、开发和留出结果、耗时、失败案例与可复现命令。未过验收时也交付失败证据，不覆盖旧权重。

## 2. 首版通信假设：分布式执行，但采用理想同步广播

为避免把“参数共享”误写成真正无需通信，首版明确如下假设：

1. 每 20 个环境步为一个高层决策窗口。所有存活无人机在窗口开始时同步广播各自状态、当前任务、目标和可共享的已知地图；它们收到同一份带时间戳的团队快照。人员位置、通信状态和 AoI 假设通过现有仿真共享视图可用。观测不含火场真值。
2. 每架无人机本地构造自己的策略输入，**独立采样/决定自己的 3 类任务**。
3. 无人机广播本窗口的任务类别。所有飞机对相同快照、相同任务消息集运行相同确定性目标分配算法，各自在本地得出一致的团队目标，并只执行自己的那条指令。
4. 一次高层决策有两轮信息交换：状态/地图广播、任务类别广播。首版假设无丢包、无延迟、消息一致和同步；通信耗时、字节数单独记录，仿真只建立协议和数据量，不虚构物理网络时间。消息包含可用于确定顺序的唯一 UAV ID。
5. 若训练仿真仍由单个 Python 进程批量运行网络与 `env.step`，这只是模拟执行的计算实现。必须提供可独立调用的 `actor(local_obs)` 和本地目标计算函数，及多进程/逐机独立模拟一致性测试；不得把一个全局联合动作网络包装成分布式模型。

这个设计**不依赖单个无人机作为指挥节点**，但依赖两次可靠广播和全体一致的公共快照。公共共享地图/人员信息是明确的理想化假设，当前环境并未验证真实多跳路由、容量、延迟、分区或失联时可共享的全局信息。局部可见、缺包、不同步和网络退化必须作为后续扩展，不能在本阶段宣称已解决。若后续取消可靠广播，目标冲突协议必须重新设计和评估，不能沿用本实验结果推断。

## 4. 环境过程和可扩展动作

高层步 `k` 对应 `t=20*k` 环境步，首次在 t=0 决策。每个窗口：

1. 组建当前允许公开的带时间戳快照，每机根据自身状态及快照生成 `o_i`。
2. 所有存活机器使用相同参数的 `πθ(a_i|o_i)` 输出 `explore/relay/charge`。训练采样，测试使用 argmax；同分按动作编号取小值。训练随机流按 `(run, episode, t, UAV ID)` 独立派生，不让所有机器因共用随机数而强制选相同动作。
3. 广播任务选择，按第 6 节本地计算目标；请求本机高层指令。
4. 环境执行最多 20 步，并按物理步采集奖励和指标。协议可能更改任务；下个观测必须读取**实际任务和目标**，不能只读模型请求。
5. 计算团队共享 `R_k`、下一时刻观测和终止状态。600 步作为有限时域 episode 真正终点，不 bootstrap；早停必须记录原因。若以后使用人为截断，明确 `truncated` 并按配置 bootstrap。

策略没有 `3^N` 联合动作输出，也不以无人机总数改变模型维度。每台只输出 3 个概率；团队联合动作由各自输出组合形成。首版不预先强制“至少一机中继”或“最多两机充电”，否则可能将协作结论写死；统一安全充电保护照常执行。当前共享快照为全局一致视图，不应称为仅凭单机局部传感器工作。

## 5. 状态与策略输入：变数量实体，固定网络接口

**原则**：无人机数量和人员数量都不能作为固定形状前提。保留变长实体集合，网络使用共享实体编码和掩码池化；支持不同机数的 batch padding，padding 不参与平均、最大值、loss、熵或价值估计。正式模型输入结构、数值范围和缺失值写成 `obs_v2`，并保存各字段规格。

每架 i 的观测由以下组成，连续量按固定物理尺度归一化和裁剪；归一化范围由训练前配置给出，不用留出集拟合。

### 5.1 自身向量 `self_i`，16 维

`x, y, energy, signed_return_margin, nearest_pad_steps, task_explore, task_relay, task_charge, target_dx, target_dy, has_target, current_task_age, goal_complete, charge_protection_active, stalled, alive`。

坐标与距离按地图尺度，能量按最大电量，任务年龄按 100 步裁剪。返航余量采用 `energy - cost*steps_to_pad`，再按最大能量缩放；距离由当前 `ChargeProtocol` 实际站点和步数口径计算，不宣称物理安全保证。任务 one-hot 用保护后的实际任务。`stalled` 为最近 10 个物理步位置不变且未在站内充电；历史不足时 0。缺目标相对坐标为 0、`has_target=0`。

### 5.2 队友集合 `teammates_i`

每位其他无人机使用与 self 一致的 16 维实体向量（坐标或相对位移的语义需在实现中固定并记录）。对于每机独立的状态，排除自己；使用带掩码的共享编码后 `mean` 和 `max` 池化，另提供队友数量和无队友标志。空集合的池化全零。加入数量特征可以识别机队规模；改变 ID 或实体输入顺序不应改变网络数值输出（除浮点容差）。

### 5.3 人员集合 `persons`

每个人 8 维：`x, y, covered, aoi, distance_to_base, nearest_uav_distance, known_fire_flag, exists`。人员数量可变，同样经共享编码和 `mean/max` 掩码池化，附人员计数及空集合标志。AoI 使用当前值而非历史最大值；`covered` 表示基站或 UAV 有通信。`known_fire_flag` 仅在有明确可观测数据时启用；当前环境若只有人员共享已知火图而不是逐人地图，则使用**所有人员一致的共享已知标记**，不能假装是逐人事实；无法提供则统一置 0 并记录。人员 ID 仅用于目标协议排序，不作为模型学习的连续特征。

### 5.4 团队摘要与已知地图

团队摘要包含：t/600、剩余时域、已探索比例、UAV 覆盖比例、总通信覆盖比例、平均与当前最大 AoI、无通信人员比例、已知火情区域数、已知火情格比例、未知格比例、当前 explore/relay/charge 比例、电量最低/平均值、最近窗口探索增量、总通信覆盖均值、失联比例均值、充电保护率。机数和人员数用固定尺度归一化并另存原始值。各比例按实际存活机数或人员数计算；空集合情况统一定义为 0。首次窗口无历史置 0。

将 `shared_cache(e)['M']` 中允许共享的已知地图分成 5×5 区域，各区域含未知比例、已知燃烧比例，共 50 维；动态人员/无人机的数量不会改变地图向量长度。模型输入共享地图相当于理想地图广播假设。应审计现有共享地图如何生成，不能说成各机传感器天然共享。

### 5.5 Actor 与 Critic

Actor 由 self 编码、队友共享实体编码与掩码 mean/max、人员共享实体编码与掩码 mean/max、地图和摘要组成，再经 MLP 输出 3 个 logits。建议实体编码为 64 维、融合 MLP 256→128，ReLU。网络不以 UAV 编号作为特征；目标协议可用 ID 打破完全对称并明确记录。

集中式 Critic 在训练时接收**同一时刻的团队可观测状态集合**（可复用实体池化结构、无固定 N），输出一个共享团队价值 `V(s)`。不要让 Critic 使用火情真值或未来信息；这样简化训练部署口径。Critic 仅用于训练，部署每机只加载 Actor 和必要归一化信息。

策略输入严禁：`sense_state()` 的 `discovery`、`burned`、`rescuer_known` 等可能依赖真值的统计；`task_metrics()` 的真实燃烧/过火/扑灭；未来信息、reward 或真实火图。需要做真值隔离测试：固定所有允许输入、独立修改仅用于统计的真值而不刷新已知地图时，输入向量、策略 logits 和目标应不变；改变合法观测时则应产生对应变化。测试实体重排及 N=1/3/4/6/8 的 padding/掩码行为。

## 6. 无中心节点的目标生成与冲突处理

模型只选择任务类别。实际任务还需要探索目标、relay 人员和充电站。每架无人机收到同一个公共快照与**所有机器的任务类别消息**后，本地运行完全一致的以下确定性算法：

1. 确认快照版本、时刻、参与机 ID 和类别消息齐全并一致；首版缺包/分歧场景不纳入主测试且记录协议失败，不可伪装成可靠广播。
2. 用 UAV ID 升序遍历参与机；相同状态与消息应得出同一个全队计划。已经有同类且有效的目标优先保留并先占位。新任务和无效目标按下面规则生成。算法在每台无人机独立算一遍，训练器收集指令仅为推进仿真，不替它们做决策。
3. 对 explore，将公开已知地图分为 5×5 的 20×20 区域，优先选未知格数最多且本窗口未被其他 explore 机占用的区域；相同未知格数选距离本机更近（切比雪夫距离），再选区域编号更小者。目标为区域中心。若探索机多于可用区域，允许重复但记录。未知全为零时，优先复查已知火情区域；有可信观测时间戳时选最久未更新的，否则按固定区域编号轮转并标记 fallback；没有已知火情则轮转全图区域。不读火情真值，不暗中输出 patrol。
4. 对 relay，人员按 `(无通信优先, AoI 降序, rescuer_id 升序)` 排序，已保留目标先占位，再为新 relay 机逐一分配尚未占位者；人员数不够时允许重复并标记。无人员时使用无目标 relay 兜底并验证环境能解析。人员 ID 为环境中的 1-based ID，不能用列表位置冒充。
5. 对 charge，输出 `{"task":"charge"}`，站点由共同充电保护在各机执行时解析。该协议所用的是现有环境能力，不表示已经实现真实分布式充电排队。

保留与重分配时应给每个目标状态明确的有效性定义、时间戳、去重规则和失败日志。UAV ID 排序是工程上的确定性破对称，会带来编号偏置：网络本身无需 ID，但最终分配可能受 ID 影响。须做 ID 轮换评测并报告，不宣称全系统具备严格置换等变性。通信消息包含完整动作集合而非只有自己的动作，这是与单机自主决策不同的全队协商假设。

训练和测试均使用相同协议。测试至少包括：同一快照不同遍历输入顺序得到相同输出；多架同时 explore/relay 的分配和目标占位；无人机数量变化；每台本地计算得到的目标与仿真实际计划逐项一致。不得只以集中式的输出替代上述一致性验证。

## 7. 训练奖励：团队任务目标及各机安全

每个高层窗口使用同一个团队奖励；每个物理步记录分量并累加。定义：

- `B_j=sum(burning_state>0)`：累计过火格，含当前燃烧、烧尽及已扑灭；`ΔB_j=max(0,B_j-B_(j-1))`。
- `L_j`：真值未合围燃烧格，环境已有 `_active_true_burning_mask` 的口径，核对实际实现和缓存；无法正确获取则记录问题而非静默替换为全部活火。
- `C_j`：基地或任一 UAV 总通信覆盖比例；不同于仅 UAV 的 `coverage_rate`。
- `X_j`：共享已知地图本步新探索格数。
- `ΔD_j`：本步首次在站外耗尽的无人机数量。

初版分解：

```text
r_j = - 0.020 * ΔB_j
      - 0.002 * (L_j / 100)
      - 0.010 * (1 - C_j)
      + 0.005 * (X_j / 100)
      - 5.000 * ΔD_j

R_k = sum(r_j in window) - 0.020 * N_switch_k
```

`N_switch_k` 为模型请求与决策前实际任务类别不同的存活机数量；t=0 不计，不因目标坐标变化或充电保护二次计数。当前奖励里耗尽和切换按数量求和，机数变化会改变规模权衡；这是**明确的首版选择**。必须按机数诊断分项量级和人均耗尽/切换率，并在开发集比较归一化版本 `ΔD/N_active`、`N_switch/N_active` 的效果；不同版本视为独立实验，最终测试前固定，不可见结果后回选。若直接计数导致模型回避更大机队的必要切换，需如实分析。

奖励的过火、未合围使用仿真真值，是**训练时特权奖励**，禁止进入 Actor、消息、目标或历史。部署无需计算奖励。不要奖励活火归零，因为烧尽也能导致归零；不可将扑灭数单独当作最终目标。报告灭火、烧尽、累计过火、未合围暴露、探索、通信、AoI 和能量等原始指标，不以 shaped reward 代替任务成绩。

训练前对每个机数 3/4/5/6，用随机、H3 各 20 个训练专用场景做完整回合，输出各分量的分布与性能；可根据结果在正式训练前冻结更合适的权重并版本化。奖励数值只是初始值，不表示已优化。

## 8. MAPPO 实现与运行设置

独立目录 `experiments/local_allocator/`，输出 `research_outputs/local_allocator_mappo_20261103/`；不要修改旧模型或覆盖结果。文件建议：`env.py`、`observation.py`、`broadcast.py`、`targets.py`、`reward.py`、`model.py`、`mappo.py`、`train.py`、`evaluate.py`、`baselines.py`、`tests/`、`README.md`、`configs/`。

首版具体算法：

- 同一 `πθ` 处理所有无人机的各自观测；每机 3 类 categorical distribution。共享参数提供规模扩展，不意味着共享动作。
- 集中式 Critic 输出一份团队价值 `V(s_k)`，使用团队奖励做 GAE。`gamma=0.97`、`λ=0.95` 均以 20 环境步的**高层步**为单位。
- PPO 采用逐机概率比 `ρ_i=πθ(a_i|o_i)/π_old(a_i|o_i)`，对每台的 clipped surrogate 乘相同团队优势，按 active mask 在所有有效 agent-time 样本上求平均；团队价值 loss 每个团队时间步只算一次，防止机数越多 Critic 被重复加权。写清变机数 batch 实际采样/加权方式并报告；可补充按 episode 加权消融。
- 初始超参：clip 0.2，Adam actor/critic 学习率各 `3e-4`，value loss 系数 0.5，entropy 系数 0.01，梯度范数 0.5，每批 4 个 PPO epoch；按有效 agent-time 样本构造 minibatch 256。训练数据每次收集约 2048 个**团队高层转移**，实际每 batch 有效 agent-time 数随 N 变化，记录两种计数。首轮可根据吞吐缩小并记录。
- checkpoint 包含 Actor、Critic、optimizer、归一化、更新计数、配置与 Python/NumPy/Torch/环境 RNG；如在 rollout 中断也要保存未消费数据或明确只支持批次边界恢复。测试采用确定性 argmax。

环境全局 NumPy RNG 和 cwd 可能被修改。优先使用独立进程而非线程隔离 worker；明确 episode seed 和策略随机流，先验证同 seed 完整回放与不同 seed 不同初态。每个 worker 不得复用相同全局 RNG。

训练起点：3 个独立训练随机种子，每种子 2000 局；每种子训练 3/4/5/6 机各 500 局，场景 seed 不重叠，均匀抽取机数并记录。物理步上限 600/局。先测 10 局各机数的实际耗时、内存、每轮消息量与吞吐，估算总预算；如资源不足，保留可恢复结果、如实说明缺失项，不假装多种子完成。每 100 局使用分机数开发集评估，基于**整局任务指标**而非训练奖励选 checkpoint。超参、奖励或协议改变另开版本并保留所有结果。

## 9. 对照与公平比较

所有主对照必须使用**相同 3 类动作、20 步周期、相同可观测信息、相同广播/目标协议、相同冻结底层 Actor 和充电保护**。不要让 RL 获得更强的目标生成器。

1. **随机分布式策略**：每机独立均匀选择 3 类动作，随机流独立，可复现。
2. **固定角色**：通过公开机号排序，按机队比例分配任务（例如约 50% explore、25% relay、25% charge，余数按固定顺序补齐）；全部使用同一目标协议。明确这只是弱参考。
3. **三动作启发式 H3，主强基线**：从所有可观测机队状态出发，低于电量阈值的机体按电量排序主动 charge，其他机器按人员 AoI、链路与距离选择 relay，其余 explore；规则需适配任意机数，指定具体边界/平分/人数为 0 的规则并配置化。在开发集按事先固定的小网格选充电阈值 `{220,260,300}` 和 relay 数量方案（固定 1、按机数比例），记录搜索预算。若 H3 在测试时由单进程集中计算，应诚实标注；另提供各机用相同公共快照重复计算 H3 的版本以测通信与分布执行成本。
4. **共享本地策略的消融**：无队友集合、无人员集合，或不提供广播的任务消息而以固定本地规则选目标，分别检验团队信息和目标协商的作用；缺广播版本不能声称仍然执行一致的去重协议。
5. **原项目启发式 H**：`lowlevel/mission_demo.py::brain` 有可能输出 patrol、使用不同目标协议与信息；只作为既有系统参考，注明动作集合和接口差异。

有条件可设同样总训练步数的中心化 MAPPO 参考，但不允许它的信息和目标特权不对等。比较每机数的任务性能、调用延迟、消息量和通信轮数；不要只展示 4 机或只报相对随机的优势。

## 10. 场景划分、模型选择与验收

运行前核对以下 seed 未与历史正式测试重复；若冲突，创建新范围并把完整列表存入配置。训练随机 seed 与场景 seed 分开。

- 训练：`980000–985999`，3 个训练随机种子各 2000 个不重叠场景；每种子 3/4/5/6 机各 500 个。
- 开发：每机数从 `986000–986159` 中划 40 个独立场景；用于选择 checkpoint 和 H3 参数。
- 留出测试：每机数从独立的新 seed 段划 100 个场景，3/4/5/6 各一组；资源不足至少各 30 个并标 provisional。最终测试模型、参数、协议和脚本必须先冻结。
- **规模外推**：7、8 机从其他独立 seed 各至少 30 场景，仅在环境、站点、性能及广播协议支持时运行；无训练中这两种机数。逐项报告为外推测试，不能与训练规模混合平均。必要时额外改变人员数/火势作为单列的分布外探索。

`N=3–6` 的场景、地图、人员数与火势默认只改变机数，其他参数保持一致；联合资源可用性自然随 N 变化。还可做固定比例改变人员数的额外分层，但需另报。

每个训练 seed 在开发集先检查守护项，再按 3/4/5/6 等权平均的累计过火相对 H3 差选择 checkpoint；如果没有候选满足守护，保留过火最好的候选并标 failed。选定后每个训练 seed 的候选在相同留出种子评估，不只挑最好一个。每机数以 episode 为统计单位，报告 H3 配对差、均值、中位数、场景级 bootstrap 95% 区间、逐训练种子结果和全量失败；不可把单机/窗口当独立 episode。

**首版工程验收门槛**：

- 分布式契约：每台调用同一 Actor 输出 3 维，N 改变无需改权重或网络形状；所有有效机有合法任务；同一快照不同进程各自计算出的目标一致；padding、实体重排、真值泄漏、同步广播和保护覆盖测试通过。
- 任务主目标：3/4/5/6 四个机数各自相对 H3 的累计过火配对均值下降至少 5%，同时报告区间。这个门槛较严格、只是工程目标，没达到如实报告；区间大幅跨 0 不能声称稳定改善。
- 守护：各机数相对 H3 平均站外耗尽数增量 ≤0.1；总通信覆盖均值下降 ≤3 个百分点；UAV 覆盖、AoI p95/最长失联、终局探索、活火和烧尽均分开报告，有明显退化应列明。比较两个模型期间统一保护配置，额外报告每百机步的强制覆盖率。
- 训练稳定性：3 个独立训练 seed 各自报告，不只挑最优；若只完成一个则最多 provisional。
- 未见规模 7/8：另报性能与不确定性，不作为已证实通用任意规模；局数不足或环境不支持需标未验证。

5% 及守护阈值是工程判断，非论文级非劣性证明。若某机数优势、另一些退化，要如实报告规模条件；不能仅以总体平均遮掩失败。

## 11. 分阶段执行

### A. 代码审计和环境封装

1. 记录 Python/torch/硬件、代码绝对路径与哈希、Actor 哈希、环境参数，验证 3–8 机可初始化并前进，记录充电站/人员参数是否限制规模。
2. 实现明确的 `DistributedAllocatorEnv`：一次 step 推进 20 物理步，逐步记录真实奖励分项和协议结果。`JointRuntime.run_to(t+1)` 可能引入重复统计开销；先测试，必要时抽取独立逐步适配器，并与原运行器用固定计划逐步对拍。
3. 验证同 seed + 相同动作/协议精确回放，不同 seed 初态不同；确认无跨 worker 全局 RNG 污染。
4. 测试三动作解析、状态维度与变长掩码、实体重排、通信双方一致、relay ID、目标去重、保护覆盖、地图数据来源、真值隔离和终止类型。
5. 跑各机数 10 局吞吐，进行奖励分量审计和协议测试。若共享快照与部署设想不符，先按本方案理想广播构造，不得暗自改为单机局部观测后照搬结果。

### B. 基线、训练与消融

1. 对每机数预先运行随机、固定角色、H3、原始 H，并记录请求与实际任务、消息轮数和字节数。
2. 单场景过拟合只检查梯度/接口；正式训练使用场景池与机数混合，不把过拟合当泛化。
3. 进行共享 Actor + 集中 Critic 的 MAPPO 训练，分机数评估；诊断各机动作分布、奖励、强制覆盖和梯度。对目标协议/队友信息做消融。

### C. 冻结评估与交付

1. 冻结每个训练 seed 的 checkpoint、训练配置、目标/消息协议、H3 参数、Actor 和源码哈希。
2. 在每机数的独立测试场景配对运行并输出原始数据、统计、所有失败；7/8 机单列。
3. 测试每机 actor 推理与目标计算开销、实际模拟的消息字节数和广播轮数；P50/P95/P99 注明设备、并行方式、线程及 warmup。分别报告单机本地推理与整个仿真集中批量计算耗时；理想广播不产生真实链路延迟测量。
4. 交付 `actor(local_observation)->action`、`resolve_target(local_snapshot, all_actions, self_id)->order`，消息 schema、状态版本、计时方法与测试；提供独立进程模拟的多机一致性测试。
5. 编写 `training_report.md`，包括设计变更、训练与开发选择、机数分层、3 个训练 seed、对照、指标区间、通信假设、编号偏置、执行器限制和失败。
