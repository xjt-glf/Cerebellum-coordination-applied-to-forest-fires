## 1. 先记住目前已经成立的结论

**现有底层 Actor 已具备开展高层决策研究所需的目标执行能力，下一阶段默认冻结它。此前由 Codex Agent 结合当前状态、历史反馈和工具摘要进行高层规划，在三个相同场景种子中，累计过火面积均低于当前启发式。** 这支持继续研究大脑的价值。

这个结论的对象是“当前 Agent 规划方案 + 冻结 Actor + 公共目标与充电协议”，适用范围是已测的三个场景。不能将它写成“所有大模型都优于启发式”。已有千问 API 的十局正式对照结果相反，必须同时保留。

对底层“可靠”的准确理解：合法探索目标到达、区域探索和充电已有较强实证；持续跟随移动人员仍要监控，巡逻绕圈能力不足。默认使用 `explore`、`relay`、`charge`，需要局部转弯时可选择短航迹转化器。现阶段不要求为接手大脑重新训练。

你的任务是接管高层决策，不是花几个小时重新证明旧 Critic 有缺陷，也不是照抄已有90条指令重放后宣称自己完成了在线规划。

## 4. 环境到底在模拟什么

| 项目 | 当前对照设置 |
|---|---|
| 地图 | 100×100，矩阵索引为 `[x,y]` |
| 无人机/人员 | 4架、10人 |
| 初始火源 | 3个，`n_fire_seeds_range=None` |
| 风 | 按种子随机，蔓延模型参数spread_gain=1 |
| 回合 | 600个物理步；每20步高层决策一次 |
| 单机动作 | 8方向各移动1格或悬停；斜步也只占1物理步 |
| 观测/通信 | sensing_radius=4，UAV通信半径12，基站通信半径15 |
| 人员速度 | 0.5格/步 |
| 灭火 | 地面人员自动靠近火线作业，半径2，每人每步最多2格 |
| 能量 | 满电600，每步2.5，移动/悬停/被阻挡均消耗 |
| 补给 | 进入任意真实充电站切比雪夫半径1内，在环境步结算时充满 |
| 环境内部自动高层规划 | `replan_every=0` |
| 因全机耗尽提前停局 | `terminate_on_all_depleted=False` |

无人机的核心贡献是获取火情和通信回传，人员依据已掌握的火情选作业位置并灭火。大脑看到真值不会自动让人员知道真值，也不会自动把真值灌入Actor观测。你必须安排真实的观测、地图交换和人员通信接触。

信息流应理解为：

```text
当前真值 → 大脑用于分析和下发目标
无人机实际飞行 → 本机观测 → 环境规定的地图交换/通信
人员掌握的地图 → 地面目标分配/移动/灭火 → 下一次反馈
```

全队融合图、每架本机图和人员共享图是不同对象。覆盖率高也可能只是覆盖了一群尚未收到有效火情的人；“有人在线”与“人员掌握当前未合围火情”要同时检查。

地图编码：`?`未知，`.`健康，`f/F`燃烧，`b`烧尽，`e`扑灭。`rows_x[x][y]`才是(x,y)，不要按通常图片的行列顺序转置。数值RLE逐行沿y展开。

无人机合法移动坐标为x=1..98、y=0..98；不要给x=0或x=99的飞行目标。地形主要影响火势/人员等环境过程，当前无人机移动阻挡不是把地形高度当实体墙；主要检查边界与其他无人机占位。实际参数以本局full_snapshot.rules为准。

## 5. 你应该读取哪些状态

建议先读摘要，再按问题下钻全量当前快照，保留前几次决策和预期结果。读更多信息是允许的，但不要把机械打印一万格当作已经完成态势理解。

| 信息 | 关键字段/位置 | 用途 |
|---|---|---|
| 当前步骤、进度 | waiting.json、progress.json | 确认本轮是哪个t，避免把过时命令下发 |
| 每机位置、电量、实际目标 | full_environment.uavs | 判断航程、返航和目标是否真的生效 |
| 到访/区域完成 | goal_progress、distance_to_target | 区分未到、到达后驻留、区域尚未完成 |
| 目标人员/所有人员位置和AoI | personnel、uav_links、personnel_in_own_link | 动态分组，检查真实覆盖遗漏 |
| 未合围火场和边界 | true_fire_clusters、boundary_cells、true_fire | 挑选有价值的观测点 |
| 已知差距 | team_known_fire、personnel_shared_known_fire、各uav图 | 发现与传递是否脱节 |
| 未知区分布 | 摘要unknown_tiles | 火势受控后有分工地扩图 |
| 实际执行与抢占 | steps.jsonl、goal_notes、charge_overrides.jsonl、route_events.jsonl | 查指令为什么没按预期执行 |

短航迹版waiting摘要数组含义：

```text
metrics = [explored, discovery, rescuer_known, coverage, burned]
fires   = [[centroid_x, centroid_y, size, contained], ...]
U       = [[id,x,y,energy,task,resolved_target,personIDs_in_own_link,blocked], ...]
P       = [[person_id,x,y,aoi,uav_links], ...]
unknown_tiles[xbin][ybin] = 对应20×20区域的未知格数，最大400
route_feedback = 各机内部航点索引、队列是否结束、剩余点、到期时刻
```

`burned`在该简报metrics里是比例，最终summary的 `burned_cells`才是格数。unknown_tiles的5个x/y区间分别为0–19、20–39、40–59、60–79、80–99，区域中心10、30、50、70、90。

单航点版control打印的U数组更长，附有距离、完成和区域进度；不要复用短航迹版的列索引。最好读取waiting.json中的具名字段或检查compact/control实现。

AoI按环境通信阶段更新，随后人员还可能移动0.5格。快照中的当前几何链路与AoI字段可能有一步阶段差，不能凭一次不一致认定接口错误。摘要active_clusters等缓存计数也不能替代逐格真值 `_active_true_burning_mask` 的任务验收。

## 6. 我作为大脑时采用的决策方法

以下是已经用过的经验，尚未做独立消融验证；你应根据当前状态调整，不必把它们固化为唯一启发式。

### 6.1 每次决策的顺序

1. **先检查电量和实际执行异常。** 哪架要补给，哪架在站边但没充上，哪架被另一架卡住，上一条目标有没有真正应用。
2. **看真正还会扩散的火。** 哪些未合围火的边界尚未观测，哪些人员图已经过时，哪一个火场缺少及时信息。优先补有任务价值的观察。
3. **按人员当前空间分组安排通信。** 看每名人员的链路和AoI，不只看平均覆盖。人群分流后，一架早期中继不够覆盖全队。
4. **提前安排交班。** 将充电完成机移动到原中继附近，再让低电机走。对计划需要20–40步交接的情况提前一个窗口行动。
5. **检查探索目标的增量价值。** 已完成目标换新目标；火势受控后释放多余感知机，分工补地图空白。
6. **决定用一个点还是短折线。** 直线用单点；20步内需要绕侧或跨相邻扫描带才用短航迹。
7. **明确下一窗口期望看到什么。** 哪个人恢复覆盖、哪块边界被看见、哪架到站、哪条航迹应该完成。下一次用实际反馈核对。

### 6.2 开局经验

在已测三个场景中，人员起步集中于西侧基站附近，三火场分散。有效起手经常是1架向人员组做中继，另外3架分赴不同火场，从有利于观察边界的位置接近，而不是先均匀刷全图或让两架重复跟同一人。

分配依据是当前距离、剩余电量和未来任务，不按固定机号。远端火场需要及早派机：20步内到不了不代表这个直线目标不该给；只要持续有进展，可以跨窗口保留。

这只是当前场景的起手思路。新种子如果人员已分散、火场很近或初始电量不同，应重新判断。

### 6.3 火场刷新与位置选择

- 传感半径只有4格。仅飞到火场“附近”，可能仍没覆盖关键边界；火场质心也不自动是最佳观测点。
- 可在相邻侧面挑观测点，避免多机重复扫描同一侧。看已知图/边界差异验证实际新增信息。
- 已合围余火不会继续向健康邻格扩散，通常应降低其侦查优先级；仍需以真值与人员图分别核对，不能把缓存的人员认知残火等同于真值危险。
- 合围后释放无人机去探索或支援通信，避免整局反复围着已失去扩散能力的火刷新。
- 火场判断变化后，写明确的新目标。不要期待冻结Actor替大脑自动理解战略变化。

### 6.4 人员分组与中继

- 优先使用 `rescuer_id` 跟踪移动人员，ID是1..10；无人机数组索引是0..3。
- 一个中继可覆盖附近多人，选择组内较有代表性的人员；分流后重新选代表或增派中继。
- 如果某人AoI持续增加、同组其他人一直在线，说明平均覆盖掩盖了边缘遗漏，应单独调整位置或指定该人。
- `relay`到达并不保证之后一直钉住该人。若Actor停在通信边缘导致移动人员离线，可改用明确 `explore` 航点将它带入组内，再恢复relay。标签是位置控制接口，任务价值以实际观测/链路判断。
- 记录自己为何临时用explore兼顾通信；不要在报告中把所有explore时间都当作有效搜图时间。
- 指令变更后会改变后续覆盖、地图和人员路径，整队轨迹可能长期分叉。这不等于一架改指令就必然使其他Actor首步动作大变；旧诊断已纠正过这种机制误判。

### 6.5 充电：最容易让完整任务失败的细节

真实站点只有：

```text
(10,10) (10,90) (90,90) (90,10)
(10,50) (50,10) (50,90) (90,50)
```

**(0,50)是通信基站，不是充电站；(50,50)也不是站。**

用8方向移动的理想到站下界估算：

```text
steps_to_pad = max(0, ceil(max(|x-sx|, |y-sy|) - charge_radius))
required_energy = 2.5 × steps_to_pad
公共ChargeProtocol保护线 = required_energy + 2.5 × 12
```

这没有计算Actor绕行和相互阻挡，应提前交班。充电协议是底线，不负责做优质的团队排班。

- 大约每个20步窗口耗50电；不是“悬停就省电”。
- 指定最近且合法、可达的真实站；不必回固定(0,50)，也不必坚持最初分配的遥远站。
- 在站旁2–3格不等于已进有效半径1，必须看energy是否回满、at_charger/recharged等实际字段。不要看到recharge标签就立刻给离站任务。
- 默认不在尚未到站时切回工作；否则它可能带着低电量再次远离站点。
- 充电在环境步结算时补满；普通探索路径恰好经过站也能充电，要依据真实电量更新判断。
- 站外零电量会无法移动；不能靠改目标让它复活，更不能改电量掩盖失败。
- ChargeProtocol可能清空order的target，实际站点保存在部署站点解析中；查resolved_target、selected_charger及charge_overrides，不要只看JSON里target=null就认定丢失站点。

### 6.6 卡住、抖动和目标完成

- 距离目标1–3格往返可能是Actor的近点行为，不代表解析失败。单点到访/区域完成/短航迹切点的容差不同。
- 相邻无人机可能想互换占位，被环境互相阻挡。检查blocked和实际坐标，给其中一架错开的临时航点，打破对顶；不要继续原样重发几十步。
- 旧单航点第三阶段曾出现两机在(30,30)/(29,29)附近对顶，给一架北侧临时目标后解除。应迁移“错开通道”的处理方式，而不是照抄坐标。
- 每20步距离是否减少、未知区域是否真的被本机观察，比“标签看上去对”更可信。
- 已完成探索目标反复重发时，公共目标管理器可能自动采样新的未知目标。必须核对requested_plan、applied plan、实际steps.orders和goal_notes。

## 7. 指令接口与短航迹契约

一次提交完整四机列表，位置即UAV0..3。不要直接输出底层action数组。

```json
{
  "seed": 730000,
  "t": 0,
  "plan": {
    "uavs": [
      {"task": "relay", "rescuer_id": 5},
      {"task": "explore", "target": [49,34]},
      {"task": "explore", "target": [85,37]},
      {"task": "charge", "target": [50,90]}
    ]
  },
  "reason": "记录当前依据、分工、补给交班和下一窗口预期。此例只展示格式，不能照搬到其他状态。"
}
```

默认三类指令：

```json
{"task":"explore","target":[x,y]}
{"task":"relay","rescuer_id":5}
{"task":"charge","target":[90,50]}
```

relay也可用固定target，但移动人员优先给rescuer_id。避免同时填互相矛盾的target和rescuer_id；契约v2优先解析实际人员目标。默认不发patrol或依赖auto半径解决绕圈问题。

短航迹的有效例子：当前UAV在(68,39)，给：

```json
{"task":"explore","route":[[62,45],[62,52],[56,57]]}
```

含当前位置的三段理想航程为6+7+6=19步。转化器仅将当前内部点写入原有explore单目标输入，Actor仍负责每一步动作。

契约：2–4个点；连续航点间欧氏距离≥4格；含当前位置的切比雪夫段长总和≤20；整条共线序列拒绝，直线用普通target；只支持explore，不给relay/charge附route；坐标须合法。

执行：每个底层步先充电保护，再route.tick，再Actor动作；20步结束调用finish_window记完成/超期。中间点距离≤2.5可切换；通过点的垂线且横偏≤2.5也可切换；近点≤4且4次不进展允许放行并记录。完成后保持末点到当前窗口结束；到期或充电抢占后不继续旧队列，下个大脑决策重新安排。

它是离散折线接口，允许切弯，不是轨迹位置/速度的精确跟踪器。20步预算也不是成功保证。58条中仍有2条没有在窗口内完成。末点提前完成后累计有250机步保持，这未必全是浪费，也说明并未消除全部驻留。

## 8. 公共协议和执行顺序：不能省掉

原网页GoalProtocol对不同source的明确改目标处理有区别。正式对照使用 `experiments/brain_comparison/run.py::CommonGoals`，统一按明确指令变更立即接收，避免某组实际上不能改目标。

共同循环应保持：

```text
reset环境、加载同一Actor、构造CommonGoals与ChargeProtocol
每20步：获取当前状态 → 由你决策完整四机计划 → goals.apply或converter.apply
每物理步：ChargeProtocol.sync → 可选converter.tick → Actor argmax → env.step
         → goals.update → 窗口末尾可选converter.finish_window → 保存真实执行记录
直到600步，记录失败/耗尽也继续按冻结验收协议处理
```

不要改Actor、换公共协议、提高决策频率、加入动作接管后仍声称只是大脑不同。如果要研究这些变化，需要另开实验组。

环境set_plan会重置势函数shaping电位，跨不同指令轨迹的shaped return不能作为任务成绩。用环境真值统计过火、有效信息、AoI、能量和执行结果。

## 10. 怎样评价你的新决策

优先级是任务损失与信息闭环，不是任意加权总分：

1. **任务主指标：** 最终累计过火、新增过火、真值未合围燃烧暴露积分、稳定无未合围火耗时、烧尽格数。扑灭数结合过火读，不能单独越多越好。
2. **信息：** 团队/人员的全部燃烧与未合围火召回，按真实燃烧格·步加权；最终/全程探索率；过时火情标记。
3. **通信：** UAV-only覆盖、含基站可用率、平均AoI、P95/P99、AoI>20占比、最差人员和最长中断。
4. **执行与能源：** 阻挡、越界、目标进度、实际改派、航迹完成/超期、全程最低电量、理想返航余量、耗尽与站外停滞。
5. **决策记录：** 请求指令和实际指令的差异、何时由公共协议接管、每次改变的理由与后续是否达到预期。

每局先算指标，再按种子等权汇总；配对比较必须用同初态、同Actor哈希、同物理步数和公共协议。不能把6000个人员时间点当作6000次独立试验。小样本先逐局报告，不给无根据的显著性结论。

稳定合围时间用逐步真值：最后一次存在未合围燃烧之后的首步；未完成记600并另列完成标志。它不等于所有余火归零，也不等于救援成功率。`summary.min_energy`在旧runner中来自终局快照；全程最低电量要从steps的全部机步重新算。

保持仿真在大脑思考时暂停，才能与已有主对照一致；若研究异步推理，就另建明确的时延实验。当前交互等待时间包含读写工具与多局调度，不能冒充裸模型推理时间。没有真实飞行动力学和物理秒映射，不虚构真实节能率、实时安全率或人员伤亡改善。
