# 执行后LLM评价与长期经验：创新性调研及建议方案

日期：2026-10-24。性质：研究判断与方法设计，尚未实现、训练或验证新方法。本文不修改当前Actor、前端或已有实验数据。

## 1. 直接回答

“决策LLM→执行20步→评价LLM解释得失→反馈给决策LLM→保存经验”可实现，也符合当前项目的实际需求。但两个基本想法以及它们的组合都有先例，单靠换一个LLM来打分、给理由，再接RAG或微调，不足以宣称方法原创。

传统RL中的标量价值网络主要估计价值，不负责输出自然语言解释；这不能推出已有LLM critic也只能打分。当前研究已有LLM评分、文字批评、执行反馈修订、持久经验和经过验证的反事实记忆。

我更看好的候选研究切入点是：**在冻结RL执行器、固定20步决策窗口下，判断反馈何时足以评价上层决策，区分规划错误、执行偏差和收益尚未兑现，再据此局部修正计划与更新长期经验。** 新颖性要通过与直接相关方法的具体比较确认，不能保证全球首次或论文录用。

## 5. 原始20步评分方案的三个关键缺口

### 5.1 状态变化与决策贡献不同

从t=0到20，火势、人员位置、补给和其他无人机都会变化。比较前后状态可以准确描述发生了什么，但不能直接回答“上条计划造成了多少改善”。即使覆盖下降，选择充电仍可能是正确的团队决策。

评价器至少应读取：初始状态、下发计划、实际应用的指令、20步轨迹、目标管理改写、充电抢占和终点状态。只给两个快照不足以区分多种执行过程。

原因分析在没有干预证据时应标记为解释假设；不能把一段流畅的理由当成因果证据。

### 5.2 20步未达目标可能完全正常

8方向每步移动1格，若目标切比雪夫距离为50格，理想到达也至少50步。20步后未到并不能判定不服从或规划错误。到站充电或观测远端火场还可能先损失部分覆盖、后改善续航或人员任务。

20步适合检查短期机制，不必适合所有任务收益。此前旧Actor的建议实验曾出现短窗任务量与整局收益不一致；该具体统计不能套用新Actor，但提醒我们应在当前权重重新检验评价时域。

### 5.3 “80分”的依据与用途不清楚

如果0–100分全由LLM自由给出，不同调用、任务阶段与模型之间未必可比。覆盖降低扣分也可能鼓励过多中继、损害火场发现。应先定义程序可算的指标、评价条件和任务优先级，再让LLM解释证据与建议修改。

有理由不代表理由正确；能诊断不代表能提出有用建议。评价模型自身也需要通过客观结果验收。

## 6. 建议的候选主方向

**面向大小脑协同的执行感知、延迟归因评价与长期经验更新。**

主问题：何时应该批评上层决策、应归因于哪一层、应当改计划还是继续执行，以及某条反馈何时足够成熟才能成为可复用经验。

候选方法有三个相互关联的部分：

1. **承诺与执行对照。** 下发高层计划时建立任务承诺，执行后检查请求计划、实际指令、动作与机制结果的一致性。
2. **延迟收益处理。** 评价器显式输出“执行正常但收益未兑现/尚无充分证据”，按目标与执行条件估计合理观察期，不强迫每20步得出好坏结论。
3. **待验证经验的回填与修订。** 暂时变化先留在工作记忆；获得足够后续证据再更新长期经验，跨版本/状态检索时重新判断适用性。

RAG是该方法的信息管理基础，LLM负责解释和局部建议；需要争取成为研究贡献的是上述机制是否减少错误批评、错误改派及错误经验传播。任何单个组件有相近先例，整体优势需要实验证明。

## 7. 具体实施

### 7.1 先保持三类模型冻结

- 决策LLM选择任务与目标。
- 评价LLM解释执行反馈，建议保持、等待、局部修正或重新规划。
- 底层仍用actor_selected.pt，哈希dfa5cdd0…9982e，纯Actor动作。

两种LLM角色第一版可用同一基础模型，使用不同提示与上下文；不要求两个不同厂商或不同参数模型。这样较容易排除“换了更强模型”的混杂。共同保留CommonGoals、ChargeProtocol及固定的route设置。

### 7.2 高层任务承诺

为每条逐机指令记录：

```text
decision_id / uav_id / issued_at
task / target_or_person / task_dependencies
expected_mechanism                 到点、覆盖某人、观测某边界、到站补能等
earliest_feasible_time              依据真实距离和执行能力的下界
expected_observation_window         合理观察区间
guard_conditions                   返航余量、必须保留的覆盖等
superseded_by / cancelled_reason
```

承诺的指标模板来自任务规范，不能让规划器自行降低要求来获得好评。飞到哪里仍由大脑决定，最短步、合法站点、通信几何等由代码检查。

第一版可用切比雪夫距离下界和当前Actor实测到达时间分布估计观察区间。进一步可用小模型预测目标剩余到达/链路恢复时间与不确定性；中途被改派的案例属于删失或取消记录，不直接贴成执行失败。

### 7.3 每20步的评价

先由程序生成证据包：

```text
计划是否真正下发；是否被充电保护/目标管理改写
目标距离和区域完成变化；实际阻挡和动作
各人员覆盖、AoI、有效火情认知变化
返航余量与是否实际充满电
任务承诺的年龄、理论可达性和当前状态
```

再由评价LLM输出结构化结果：

```text
execution_status       正常推进 / 执行偏差 / 指令已被抢占
task_status            已有正证据 / 已有负证据 / 收益未兑现 / 证据不足
evidence               引用真实字段、时刻与决策ID
causal_status          仅观察 / 解释假设 / 有配对干预支持
recommended_action     保持 / 等待 / 局部改动 / 重规划
patch                  可执行的逐机指令修改（如果需要）
next_check             何时、检查哪个可观察条件
tradeoff               补给/通信/探索之间可能牺牲什么
expires_at             建议有效期
```

如果保留0–100展示分，应从预先固定的指标规则或经过校准的偏好模型导出，并保留分项。不要把自由生成的总分作为唯一优化目标。

### 7.4 延迟反馈与归因账本

将未兑现的任务承诺保存在工作状态。未来到点、交班、通信恢复或任务完成时，关联原决策ID，更新其状态。若被新计划取消、执行器失效或场景改变，记录对应原因。

关联某条决策不等于已经证明它造成了结果。多次规划共同影响的整局收益，开发阶段通过同状态干预、预先固定的后续策略协议验证；线上只报告当前可观察证据与校准预测。不能把最后20步看到的全部改善归给最后一个决策。

评价器也应能修正自身旧结论，例如“上次覆盖下降被判断为有害，但后续证据支持这是补给交班的暂时成本”。这条修正同时更新经验条目，避免错误批评长期传播。

### 7.5 记忆存取

SQLite保存结构化元数据和证据索引，原始轨迹/快照追加归档；全文或向量检索用于召回经验。先按Actor/协议版本、任务阶段、资源条件和收益兑现状态过滤，再排序。

长期条目包含：条件、原计划、实际执行、已验证/未验证解释、建议修改、短期机制、长期任务结果、观察时域、反例、来源、失效条件和版本。

工作记忆中的“暂时覆盖下降”“尚未到点”不得自动变成永久负例；待任务成熟后决定写入、修正或丢弃。过期人员坐标和某种子专用点位也不能当普适策略。

### 7.6 数据与校验

开发集可复用当前确定性快照分叉设施，但先在新Actor与当前代码上做noop一致性校验。比较原计划与评价建议时保持相同初态、Actor、公共协议和事先规定的后续规划协议。

20步验承诺，整局验任务收益；保留有害建议、等待误判和迁移失败。线上不默认使用未来仿真Oracle。测试集固定后冻结跨回合经验；若评价持续在线适应，另定场景顺序、记忆写入和统计协议。

## 8. RAG还是微调

| 项目 | 外部记忆＋检索 | 微调 |
|---|---|---|
| 新经历入库 | 可立即添加，保留原证据 | 需构建训练集并更新参数 |
| 修改/删除错误经验 | 可按条目版本更新 | 普通微调不能保证精确删除某条知识 |
| 当前场景、人员坐标等动态信息 | 适合在工作状态/检索层提供 | 不适合把每次具体坐标写入参数 |
| 学习稳定诊断与修订习惯 | 依赖检索和提示 | 可在足够优质标签后训练 |
| 自动扩展上下文窗口 | 不会 | 普通微调也不会 |
| 本项目第一阶段 | 优先 | 等验证反馈确实有用后再做 |

建议顺序：先固定模型比较无反馈、原始指标反馈、LLM解释反馈、带记忆反馈，再加入延迟判断与经验回填。出现稳定提升后，可用有证据的诊断样本微调评价器；如做偏好训练，应由下游修订后的真实改善定义偏好，而非另一个LLM自由给分。主实验要保持决策模型不变，以免归因混淆。

## 9. 必须做的对照与消融

| 组别 | 设置 | 回答什么 |
|---|---|---|
| A | 同一大脑，无执行后反馈 | 基础成绩 |
| B | 程序指标/标量反馈 | 是否只需把指标告诉大脑？ |
| C | 朴素双LLM，每20步解释前后变化，无长期记忆 | 原始构想的增益 |
| D | C＋普通RAG，或Reflexion/ACE风格反思记忆 | 通用反馈记忆是否已足够？ |
| E | D＋实际执行归因＋延迟判断 | 新评价机制的独立贡献 |
| F | E＋待验证经验回填/修正 | 新记忆更新机制是否进一步有效？ |

重要额外对照：

- 固定40/60步评价，以及只按理想距离决定等待的规则。若这些简单方法已解决问题，就不能把复杂反馈成熟度模型当必要创新。
- 保留/去掉实际指令与充电抢占记录，验证执行归因是否有必要。
- 相同记忆预算下，立即写入反思与结果成熟后写入对比。
- 任务适配的COUNTERMEM/EvoCF或最接近的可复现组件，区分收益是否只是通用反事实检索。
- 同模型额外一次自修订、相近token/调用预算，以及强模型直接当大脑，排除额外计算与强模型替代的效果。

测试情境应有意识覆盖：目标距离小于/大于20步、需要轮充造成暂时覆盖下降、确实被占位阻挡、人员分流、场景资源变化。三旧种子用于开发，新种子作为留出测试；如研究模型随机性，应重复实际生成，而不是重复确定性重放。

主指标仍是累计过火、未合围暴露、有效人员认知和AoI，结合探索与耗尽。评价器另外报告：错误批评率、不必要改派率、有害建议率、收益未成熟误判率、经验负迁移、清空会话上下文后的表现，以及总token/咨询次数/耗时。错误批评与有害建议的标签应由预先规定的任务/机制与干预证据定义。

如果方法只让模型的解释更长、主观评分更好看，但任务无改善或过度等待，应判定主张失败。若C/D已经足够有效，可作为有用工程方案；论文仍需准确定位贡献。
